# 路表的两层输出：常驻索引一行一条，详情在随包文件里

Status: accepted (2026-10-21). Ticket #246（spec #234 实现决定 9 与决定 10 与决定 11 的后半）。
修订：[旧 ADR-0024](./0024-binding-contract-declares-binding-result.md)、
[ADR-0003](./0003-the-search-lives-in-the-child.md)、
[ADR-0006](./0006-the-two-doors-share-one-prefix.md)、
[ADR-0013](./0013-route-registry.md)。**本篇与这四篇读得不一样的地方，以本篇为准。**

## Context

[ADR-0013](./0013-route-registry.md) 把模型面散文收进了一个册子，但只收了**一半**：册子的
`TOOLS` 区（一个工具一条）填满了，`ROUTES` 区（一条路一行）是空的，空是设计——它留给本票。

于是到本票开始时，模型读到的「选路知识」仍散在**四个通道**里：

1. **自定义 section `<ptc>`** —— 两行路句（每个表面一行）加上那句 web 事实。
2. **工具描述里的选路句** —— `pi_task_codemode` 的描述里那句「用它在不会淹掉上下文时做这类活」，
   以及两条指南里「什么时候用 `ptc_run_code` / 什么时候用 `ptc_workflow`」。
3. **扁平日志（guidelines）** —— 上面那两条路由句 + 事实句（图像契约）+ 任务工具的三条。
4. **会话内注入的简报** —— 静态的那一半（「一个任务写一段程序」「把步骤批进一个程序」）
   与动态的那一半（当前绑定清单、例子）混在同一段文字里。

四个通道各自成立，但**同一件事被说了几遍**：web 那个事实在三处、图像契约在四处、`agent` 可选
那句在三个工具描述里各写一遍（#243 已把后者收成一个常量）。每一处都是踩过坑之后补的，而改一处
就漏两处。

同时还欠着三笔账：

- **索引没有预算。** 仓库里唯一的预算常量是绑定契约的（`BINDING_CONTRACT_TOKEN_CEILING` /
  `..._FLOOR`），而绑定契约按设计留在册子之外——它回答「调了得到什么形状」，册子回答「什么时候
  调、调的是什么」，两个问题不重叠。
- **指针会悬空。** 今天 `docs/` 不在 npm 包里，所以「随包详情文件」这个想法在用户机器上根本
  没有落点。
- **每 turn 重建的东西没有稳定性要求。** `<ptc>` 段是每个模型请求都重渲染的，而会话内注入那段
  是每次进入模式才注入一次；两者的差别被混为一谈了。

## Decision

**1. `ROUTES` 区填上七条路，一条一行。** 一条**路**是「一件事情的走法」，不是一个工具：建一条
任务、跑一段程序、跑一段有阶段的工作流、用内置工具、管一条任务、通到网、报一次结果。一条路若
与一个工具一一对应，那它就是工具索引，而工具索引已经是工具描述了。

**2. 每条路按表面交代怎么走（决定 10 的强制点 3）。** `how` 是**每个表面一条**：两个门在不同表面
上是两种写法（程序里的绑定 vs 脚本里的工具），「这一面不适用」也是一个答案。路里没有空洞。

**3. 常驻索引：每条路一行，详情永远不在索引里。** 索引的那一行是「路名 — 什么时候走它 — 在
这一面怎么走 — 详情的文件指针」。路的事实（`fact`）在那个文件里，不在索引里。

**4. 索引有它自己的预算。** `ROUTE_INDEX_TOKEN_CEILING = 560`、`ROUTE_INDEX_TOKEN_FLOOR = 380`
（与绑定契约同形的 ceiling + floor 两个断言，用同一把尺子：每 4 个字符 1 个 token）。**超预算时
明说**（`> WARNING:` 那一行），**不静默截断**——被悄悄删掉的一条路，是模型走不到又看不出自己
走不到的路。

**5. 索引每 turn 字节相同。** 索引是每个模型请求重渲染的，而「会话中途改系统提示词会废掉提示
词缓存」。所以索引里**不许进任何随会话变化的数据**：会话内变化的绑定清单留在会话注入那边。索引
的输入只有三样——册子的静态内容、当前表面、以及**加载时读一次**的能力开关（能不能联网搜）。
这三样在一次会话里都不变。

**6. 详情文件随包发布。** 一条路一份 `docs/routes/<id>.md`，写清怎么调、返回什么、坑、例子。
`package.json` 的 `files` 加上 `docs/routes/` 与 `docs/usage/`——今天 `docs/` 不在包里，任何指针
在用户机器上都是悬空的。

**7. 四个通道退役。**

| 今天的通道             | 处置                       | 落到哪                                                 |
| ---------------------- | -------------------------- | ------------------------------------------------------ |
| 自定义 section `<ptc>` | **升级**（不新增 section） | 同一个位置，内容换成册子渲染的索引                     |
| 工具描述里的选路句     | 搬走                       | 册子 → 由 `ROUTES` **派生**回描述（「什么时候用我」）  |
| 扁平日志               | 拆开                       | 选路的 → 册子；事实的（图像契约等）→ 工具的 `TOOLS` 行 |
| 会话内注入             | 拆开                       | 静态的 → 册子；**动态的**（绑定清单、例子）→ 留在注入  |
| binding reach note     | **退役**                   | 新模型下那条约束不存在了                               |

**8. reach note 退役。** 新模型下门是 **codemode 可达的工具**（`pi_task_codemode`），不是绑定，
于是它承载的那条约束（「只有两跳那条路」）没有了。它保护过的事实没有跟着走：**`codemode` 脚本的
工具表里没有 `pi_task_ptc`**，而这句话现在由「建一条任务」那条路的 `codemode_ptc` 分支说——
按表面说，所以它只在该说的那一面出现。note 的记录留在册子里（连同 2026-10-16 与 2026-10-20 两
次实测），因为记录是那句为什么在那里的依据。

**9. 工具描述的「什么时候用我」是派生出来的。** 描述里有一个 `route` 段落，它的文字由 `ROUTES`
算出来（`renderToolRouteHint`），不是写在那里的。于是路改了，所有在路上的工具一起改，两边不可能
漂。

**10. codemode 门的 `agent` 那句用共享常量。** 它原来用自己的话把同一件事又说了一遍。现在它用
`AGENT_OPTIONAL_CLAUSE`（与两个 PTC 工具同一份），而它多出来的那两条事实（agent 定义住在哪个目录、
起一个名字会做什么）留在它自己的 `TOOLS` 行里——那两条不是共享事实，是这扇门自己的事实。

## 证据

1. **先例不是我们的设计。** 一个在跑的 pi 扩展（`@tylerho/pi-memory`）的常驻文件就是一个**索引**：
   一条一行，详情永远不在索引里，而且索引快照整个会话稳定，因为「changing the system prompt
   mid-session invalidates the cached prefix」。另一个实现（ai-memory）确实往 `AGENTS.md` 注入，
   但那是 per-project 的知识，而且是服务端返回、由 agent/CLI 写进文件的。我们的路由是
   **per-package** 的，两个先例的做法都不适用于我们。
2. **八十七处模型面散文，二十三个源文件**（#243 的清点稿），其中**三处**已经在漂。
3. **四个通道里的重复是可查的**：web 那个事实在三处、图像契约在四处、`agent` 可选那句在三处。
4. **今天的 section 只有两行，却欠着预算与稳定性。** 它每 turn 重建，而会话内注入那段不是——
   这两者的差别正是「索引里不许进随会话变化的数据」这条要求的来源。
5. **`docs/` 不在包里**（今天 `files` 只有 `dist/`、许可证与三份根文档），所以任何指针在用户机器
   上都是悬空的；这一条是实测的，不是推断。

## 八条强制点

| #   | 规则                                                                      | 类型     | 怎么守                                                              |
| --- | ------------------------------------------------------------------------- | -------- | ------------------------------------------------------------------- |
| 1   | 工具 → 路：每个模型可见的工具至少被一条路提到                             | 机械     | `ROUTES` 的 `tools` 覆盖 `TOOLS` 的每个名字（反向覆盖测试）         |
| 2   | 路 → 工具：路里提到的每个工具名必须真实存在                               | 机械     | `tools` 的每个键必须是 `TOOLS` 的键或是那个绑定                     |
| 3   | 每条路在每个表面上都有交代                                                | 机械     | `how` 的两个表面键都非空                                            |
| 4   | 索引有 token 预算，超了要明说                                             | 机械     | ceiling + floor 两个断言，外加「超预算的渲染结果里含 `> WARNING:`」 |
| 5   | 每条路的事实段非空                                                        | 机械     | `fact` 非空                                                         |
| 6   | 工具的 description / 指南 / 片段必须是册子的调用                          | 机械     | 册子测试扫源码：册子的每一段文字都不许出现在别的文件里              |
| 7   | 索引每条路一行 + detail 指针指向的文件必须随包存在                        | 机械     | 「一行一条」+ 指针必须能解到**包内**的文件（files 字段覆盖它）      |
| 8   | 索引每 turn 字节相同                                                      | 机械     | 两次渲染逐字节相同 + 索引里没有绑定清单这类随会话变化的东西         |
| 9   | 「散文」与「形状」的边界：参数 schema 连它的 description 一起留在工具文件 | **约定** | 写进 ADR-0015 的正文，靠 code-review 守                             |

第 9 条是唯一的软点，明写**在案**：schema 的 description 跟参数定义是一体的，拆开反而更难读。
八条机械的强制点由**一个**套件守住：`tests/unit/route-forcing-points.test.ts`（#247）。第 9 条不在套件
里——它是约定，靠 code-review 守，没有一种机械写法能检查「schema 的说明就放在 schema 旁边」。
第 7 条的「怎么守」在 #247 订正过：原写「指针必须能解到**仓库里**的文件」，而仓库里有文件不等于**包**里
有文件——「`docs/` 不在包里」正是这个缺陷本身（决定 6）。现在写的是包内：包里 `files` 字段的 pattern
覆盖它，且它在包根下存在。
本篇的实测比本票的验收条件多两条（#1 与 #2），它们便宜且机械，就地做了；#247 那一票仍拥有完整
的强制点套件。

## 两层输出的形状

```
<ptc>                                  ← 同一个 section，升级后的身体
Routes — one line each: …

- Create a task — …: … Details: docs/routes/create-a-task.md.
- Run one program — …: … Details: docs/routes/run-one-program.md.
…
</ptc>
```

索引里**没有**事实段、没有例子、没有坑——那些在 `docs/routes/<id>.md` 里，模型用 pi 核心的
`read` 读。**一条路一行**是这个形状的全部承诺：模型每一 turn 只付七行的钱，需要细节时才去读
那个文件。

## 代价

1. **索引比它取代的东西重。** 实测 439 token（没有 web 那条路时）到 483 token（有它时）。它取代的
   四段散落的散文加起来差不多同样多——但那些散文把同一件事说了好几遍，索引只说一遍。**付的钱
   换的是「一处出处」，不是「更便宜」**；这一点必须说清楚，否则有人会以为索引是省钱的。
2. **指针是包内相对路径。** `docs/routes/<id>.md` 住在装好的包里，不在会话的工作目录下，所以模型
   要读它得先知道包在哪。索引里**不带绝对路径**，因为绝对路径会让索引依赖「装在哪」——而索引的
   全部承诺是它只依赖册子。**这是本篇最实在的未竟之处**，写在这里而不是藏起来。
3. **一次派发不再是一个模型的「调用约定段」。** 那条 reach note 退役了，它保护过的事实改由路按
   表面说。**这不是「实测已经不需要它」的断言**——是「新模型下那条约束不存在了」的断言；真机上
   那条路仍被走到（`codemode_ptc` 那一面），实测的教训还在记录里。
4. **索引是一个新的必守物。** 每加一条路，预算测试就多一份压力；超预算的处理是「明说」，不是
   「自动截断」，所以真正的成本落在加路的那个人身上。
5. **会话内注入的静态那半消失了。** 简报现在只说动态的事（这一场绑了什么、例子、模式状态）。模型
   仍然每一 turn 都读到「什么时候走哪条路」——在索引里，比在只注入一次的简报里**更**可靠。

## 与其它记录的关系

- **[ADR-0013](./0013-route-registry.md)**：本篇是它「本篇没有做的事」那一节里点的两件事（`ROUTES`
  区的路、常驻索引与随包详情文件）。它定的「散文只有一个出处」不变；本篇定的是那处出处的
  **形状**。
- **[ADR-0006](./0006-the-two-doors-share-one-prefix.md)**：决定 6 定的共享 reach note 退役了；决定
  6 的其余部分（同一句话在两个平面上只写一次）照旧，而且现在由 `ROUTES` 的 `how` 承担。
- **[ADR-0003](./0003-the-search-lives-in-the-child.md)**：web 那条路是它那条决定的一个**表面形态**
  ——父会话没有网，路由是「建一条任务让它去搜」。
- **[旧 ADR-0024](./0024-binding-contract-declares-binding-result.md)**：绑定契约仍在册子之外；它 §5 里
  那个把 reach note 算进 token 的测量随之过期（note 没了）。

## Reopen triggers

- **模型不再需要索引就能选路**（比如宿主自己出了路表）——那这一层可以退役，册子只留 `TOOLS`。
- **详情文件变成可被宿主索引的东西**（比如 pi 的 `read` 能按包名解析路径）——那指针可以换成宿主
  能解的形式，代价那一节就少一条。
- **索引的预算被证明太紧**（真机上模型因为索引太短而选错路）——那是调 ceiling 的时机，而不是改
  形状的时机。
