# 「等不等」是一个参数：`wait` 取代 `background`，默认不等

Status: accepted (2026-10-21). Ticket #239（spec #234 实现决定 5 与决定 8）。修订：[ADR-0016](./0016-ptc-dispatch-binding.md)、[ADR-0022](./0022-background-dispatch.md)、[ADR-0053](./0053-every-dispatch-is-a-task.md)、[ADR-0054](./0054-the-two-doors-give-one-object.md)。**本篇与这四篇读得不一样的地方，以本篇为准。**

## Context

到 2026-10-21 为止，本包里有**一个**派发入口、**两条**派发路径。`pi_task_ptc`（ADR-0052 之后的门名）接受一个 `background` 布尔量：带它走「后台」那条，不带它走「前台」那条。

那两条路径不是同一个入口的两种写法，是**两套实现**。闸门顺序、铸 id、占槽、建记录——四件事各写了一遍；深度闸的拒绝文案也写了两遍，于是同一个拒绝在两个面上读起来不一样（后台那份多一句「去看 `ptc_task_list`」）。

而那个布尔量的默认值是**「不带」**，也就是说：**一次普通的调用会等**。等一个孩子跑完、等它把答案写进记录、等它把答案带回调用方。

spec #234 的决定 5 问的是另一件事：**「这个调用点需要结果吗」**（Kotlin 的 `async`/`await` 判据）。决定 8 的原型把默认写成「默认不等（`wait` 省略）」。

为什么只能是**参数**，不能是「调用方自己 `await` 一个句柄」：结果是一次性穿过结构化边界的值，句柄里的 promise 带不回来——codemode 那侧更硬，工具 `resolve` 成结构化数据，promise 根本传不回来。剩下的只有「一个参数」和「两个入口」两条路，而两个入口 = 2 门 × 2 等法 = 4 个名字，模型面前的调用表直接翻倍。

## Decision

**1. `background` 退役，改成 `wait`。** `wait: true` = 等这个任务完成，结果在返回值里；**省略 = 不等**，立刻返回句柄，完成时通知回到父会话。**默认值翻转。**

**2. 等与不等是同一条路径上的同一个参数。** 闸门顺序、铸 id、占槽、建记录——四件事在两个等法上是**同一段代码**，不是两份拷贝。只有最后一步不同：调用方等不等。

**3. 不等的调用不等槽。** 满员时它**进队列**（ADR-0056），立刻返回句柄（状态是 `queued`），孩子等槽排到时才真的起。这正是 libuv 线程池的形状：提交立刻返回，work item 等 worker 空出来。

**4. 句柄里的标签默认取任务摘要的前缀**（64 个字符，与记录上的标签同宽）。句柄与结果带的是**同一个**标签。

**5. 两种等法下失败结果的形状相同。** 被拒绝时——不论等不等——拿到的都是**拒绝结果**（`status: "rejected"` 加 `errorMessage`），**不是句柄**。句柄说的是「这个任务在跑」，而被拒绝的任务从来没跑过。

**6. 结果上的两个字段改名。** `recordId` → `taskId`、`recordLabel` → `label`。句柄与结果从此用**同一套名字**称呼同一个任务。

这个改名本来是被一个探测挡着的：`src/tools/subagent.ts` 当年是靠「结果上有没有一个**字符串** `taskId`」来认出「这是一次后台派发、返回了句柄」。若前台的结果也带 `taskId`，每一次前台调用都会把自己当成句柄，模型拿到的是「Started task …」而不是孩子的答案。ADR-0054 已经把那个探测换成 `status`（`isDispatchHandle`），所以这道挡没了。

**7. 深度闸的拒绝只有一套文案**，两个等法共用：`dispatch depth limit reached`。那串文案正是**孩子自己的 prompt** 里承诺的那一句（深度提示块原话如此），后台那份多一句的文案让那个承诺在后台面上是假的。现在两边都是真的。

## 「不等」的那一面：孩子活过这一次调用

`wait` 省略时，这个孩子**不随调用结束而结束**。三件事因此归到「不等」这一侧：

- **R1 的会话标志**（`--session-dir` / `--session-id` / `--name`）：活过这次调用的任务要能被找回来，靠的是它的会话文件。
- **子进程环境里的任务 id**（`PI_PTC_TASK_ID`）：孩子自己再派发时，好把父任务 id 盖在嵌套记录上。
- **停止观察者**：模型用 `ptc_task_stop` 停一个活着的孩子时，真正的信号由这里发。

**等的**那一侧不需要这三样：答案当场回来，会话文件是调用方的事；而等着的调用方有自己的截止时间（`ctx.signal`），中止就等于杀掉孩子。

这就是「这个孩子活不活过这次调用」这一个问题的三个答案——参数决定的只有这一件事。

## 代价

**返回的形状随参数变，模型可能以为要结果却拿到句柄。** Kotlin 管这叫「await 遗忘综合征」。本包靠三样兜：

1. **参数描述文案**明写「传 `true` 才是等」，并说明省略时拿到的就是句柄；
2. **句柄明写**自己是什么——`Started task <id> — it runs on; read its result with ptc_task_output`；
3. **任务输出是兜底通道**：没等的那个任务，结果在 `ptc_task_output` 里读得回来。

**默认值翻转对既有程序是破坏性的。** 以前 `pi_task_ptc({ task })` 等结果，现在返回句柄。一个想要答案的程序必须改成 `pi_task_ptc({ task, wait: true })`。这是本票明确要的翻转（票面：「省略即**不等**（默认值翻转）」），代价由写程序的人承担。

**排队中的那个任务，句柄回来时还没有进程。** 这是「不等槽」的定义，不是缺陷：句柄的状态写着 `queued`，孩子等槽排到时才起。

**早退的那条路不再抛异常。** 以前前台在「写 prompt 文件 / 拼 argv」失败时抛，后台返回一次拒绝。统一之后两条路都返回**拒绝**：「never rejects」是 `dispatch()` 一直写在文档里的契约，而一次等待的调用方与一次不等待的调用方不该在这件事上被区别对待。

## 证据

1. **两条路径确实各写了一遍。** 改动前的 `dispatch()` 里，深度闸、铸 id、占槽、建记录各有两份；深度闸的拒绝文案有两套（`dispatchDepthLimitReached` 与 `backgroundDispatchDepthLimitReached`）。改完之后 `dispatch()` 只有一份，且那条拒绝文案只剩一个生成器。
2. **一个结果与一个句柄必须用同一套名字。** ADR-0053 当年给结果另起名字（按「记录」命名），理由是那个「有没有字符串 `taskId`」的探测；ADR-0054 把探测换成了 `status`，理由随之消失。判别靠 `status`：**句柄**永远是 `"running"` 或 `"queued"`，**结果**永远是 `"fulfilled"` 或 `"rejected"`——这一个字段两形状不可能共有。
3. **「不等槽」测得到。** 一个只容一个孩子的计数器，第二个不等槽的调用**当场**返回 `queued` 的句柄，且那一刻还没有第二个子进程；等的那一个则要等槽位空出来才起。
4. **两个等法的拒绝形状相同。** 深度闸在两个等法下返回同一个对象：同样的字段、同样的值、同一串文案。
5. **默认翻转是票面写死的**，不是本篇的发明：ticket #239 的验收条件第一条就是「省略即**不等**（默认值翻转）」，spec #234 决定 8 的原型写着「默认不等（`wait` 省略）」。
