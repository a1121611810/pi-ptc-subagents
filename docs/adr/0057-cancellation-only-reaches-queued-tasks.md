# 取消只对「还没起进程」的任务生效：抽掉排队中的，走信号阶梯的照旧

Status: accepted (2026-10-21). Ticket #241（spec #234 实现决定 6 的最后一段与决定 7）。修订：[ADR-0022](./0022-background-dispatch.md) 的后台生命周期与 §"What we add" 6、[ADR-0050](./0050-ptc-off-stops-new-dispatch.md) 决定 1 与决定 3、[ADR-0053](./0053-every-dispatch-is-a-task.md) 决定 4 的露面条件、[ADR-0056](./0056-admission-queues-instead-of-rejecting.md) 决定 7 与 §"遗留"。**本篇与这四篇读得不一样的地方，以本篇为准。**

## Context

ADR-0056 把「满了不拒绝」落地了：超出并发上限的请求**进队列等**，而**入队即建记录**——排队的那个任务当场就是一条 `queued` 记录，有 id、有标签、在 `ptc_task_list` 里看得见。

于是模型面前出现了一个它看得见、却管不了的东西：`ptc_task_stop` 对一条 `queued` 记录是**非法迁移错误**。registry 的 stop 边只有 `running -> stopping`，状态机里没有 `queued -> stopping`——那条记录还没有进程，没有信号可发。于是 ADR-0056 的 §"遗留" 把它记成下一步：「模型面主动取消一个排队中的任务（`ptc_task_stop` 对一个 `queued` 的任务）是下一步的事」。

同一篇的 §"遗留" 还记了第二件：「`/ptc off` 的截断语义（「停收新的 + 抽掉排队中的 + 在跑的照常」）是另一票的事」。那一句的形状今天没有着落：`/ptc off` 只停收新的，队列里排着的那些既不会被抽掉，也不会被告知。

形状的来源是 libuv 的 `uv_cancel`，也就是本篇要照着写的那条边：还在队列里的 work item 抽得掉（调用返回 0）；已经被 worker 接手的不行（调用返回 `UV_EBUSY`），它继续跑。

## Decision

**1. 取消只对「还没起进程」的任务生效。** `ptc_task_stop` 打在一个 `queued` 的任务上，走的是 `queued -> canceled`：它被抽掉出队，**永远不起进程**，记录上带着理由（`stopReason`）。它不走信号阶梯——没有进程可发信号。

**2. 已经起进程的任务取消不了，走今天那套信号阶梯。** `running -> stopping` 由模型这次 stop 触发，真正的信号由 dispatcher 发，子进程关闭时由 registry 写下终态 `canceled`。这一段行为一字未改，本篇只补上「排队中的那条走另一条边」。

**3. 记录先写终态，队列后抽。** registry 先把记录写成 `canceled`，**再**把队列里的那一条抽掉。顺序反过来会留一个窗口：槽位刚好在这两件事中间空出来时，被抽掉的任务仍然会拿到槽、仍然会起进程——而它的记录已经是终态了。写成终态在前，拿到槽的那一侧就会撞上「`canceled` 不是 `running` 的合法前态」这条边，于是它不起进程。

**4. 抽掉排队者要把它叫醒。** 队列里那一条被抽掉时，排队的那一侧被唤醒（`onWithdrawn`）。否则前台那个在等槽位的调用会一直等到程序自己的超时才结束——而它等的那个槽位永远不会来。前台因此多了一个结局：「被抽掉」，调用方拿到一次**明确写着原因**的拒绝，而不是一个挂着的 Promise。

**5. 前台程序中止抽掉排队的请求，这一条保留。** ADR-0056 决定 7 已经做了一半（ticket #240 落的），本篇验证它、保留它，并让它与决定 1 走同一条边：中止是「抽掉排队中的请求」，模型面主动 stop 也是「抽掉排队中的任务」。

**6. `/ptc off` 的确定语义是三件事。** **停收新的 + 抽掉排队中的 + 在跑的照常。** 在跑的那些是独立进程，off 的生命周期够不到它们——这与 ADR-0050 决定 4「关的那一刻要说清楚在跑的那个怎么样」是同一个形状：通告里明写「NOT affected」，而排队中被抽掉的那几条明写抽掉了几条。

**7. 生命周期面跟着「有没有记录」走，不跟着「有几个在飞」走。** 这是 ADR-0053 决定 4 已经定下的规则，而 ADR-0053 与 ADR-0050 都点名说 `src/index.ts` 里还有一格没对上：PTC 关着、而会话里有一条**已经跑完**的记录时，那三个工具仍然被从 active 集合里摘掉。补上它是一行改动——问「这个会话有没有任何任务记录」（`taskFaceVisible`），而不是「有几个在飞」。

## libuv 的证据

libuv 的线程池是这个形状的来源。下面的每一条都能在 `libuv/src/unix/threadpool.c` 里读到（`v1.x` 分支，2026-10-21 取）：

| libuv 线程池                                                             | 我们                                           | 出处                                                                                                                                                                         |
| ------------------------------------------------------------------------ | ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `uv_cancel`：还在队列里的能抽掉（返回 0）；已经开始执行的返回 `UV_EBUSY` | 抽掉一个还在排队的任务；已起的不行，走信号阶梯 | `uv__work_cancel()`：`cancelled = !uv__queue_empty(&w->wq) && w->work != NULL;`——还在队列里且还没被执行就是可取消的；worker 接手后把 `w->work` 置空，于是取消返回 `UV_EBUSY` |
| work item 一旦提交就存在，调用方一直拿着这个 handle                      | **入队即建任务记录**（状态 `queued`）          | `uv__work_submit()` 把请求装好并 `post()` 进去                                                                                                                               |
| 队列里的请求没有超时                                                     | 排队等待无超时                                 | 队列路径上没有任何计时器                                                                                                                                                     |

`uv_cancel` 的那句「还在队列里」与「已经被 worker 接手」的分界，正是本篇决定 1 与决定 2 的分界：**取消的作用域是「还没起进程」的那一段**，不是「正在跑」的那一段。libuv 自己也不假装能取消一个已经在跑的 work item——它返回忙。

## `/ptc off` 现在是什么意思

三件事，一句话：**停收新的 + 抽掉排队中的 + 在跑的照常。**

- **停收新的**：闸在 `dispatch()` 里，两个面都经过它，被闸拒掉的请求不铸任务 id、不占并发额度、不起进程（ADR-0050 决定 1，不变）。
- **抽掉排队中的**：排在队列里的那些被抽掉出队，记录写成 `canceled` 并带上理由。它们没有进程可发信号，所以这不是「停掉」，是「撤回」。
- **在跑的照常**：它们是独立进程，off 够不到；通告里明写「NOT affected」，它们继续跑、继续可查可停。

三条合起来，off 才有**一个**确定的意思：**这一关只影响还没开始的那些。** 已经跑起来的不受影响（ADR-0050 决定 4），还没跑起来的被撤回（ADR-0056 的队列是无限期的，等下去是无限期的等待）。

## 代价

**一次 registry 写 + 一次队列操作。** 抽掉一个排队中的任务写一条终态记录（与前台派发多付的那两次写同一个量级，ADR-0053 实测约 1.7 ms，而它发生在一个**本来就要等**的时刻），队列那一步是 O(1) 的一次数组查找。

**`ptc_task_stop` 的返回多了一种形状。** 它的 `status` 字段过去只可能是 `stopping`（活的子进程）或报错；现在还可能是 `canceled`（被抽掉的排队任务）。模型面读到的是一个明确的事实——「这个任务已经不在队列里了」——而不是一个含糊的中间态。

**前台那一次派发多了一个结局。** 在等槽位的前台调用，除了「拿到槽」与「被中止」，还有「被抽掉」，它拿到的是一次拒绝，消息明写原因。不那样的话，它会挂在队列上直到程序自己的超时——而它等的那个槽位永远不会来。

**模型面的散文多了一句要维护。** 「取消只对还没起进程的任务生效」这句话要同时出现在工具声明与系统提示的 guideline 里，所以它被收成一个共享常量（`TASK_STOP_SEMANTICS`），两边引用同一份，而不是各写一句。

## 与其它记录的关系

- **[ADR-0022](./0022-background-dispatch.md)**：后台任务的生命周期归它管。本篇给它加了一条边——`ptc_task_stop` 现在也能够到一条**还没起进程**的后台任务（`queued -> canceled`）；其余不变。
- **[ADR-0050](./0050-ptc-off-stops-new-dispatch.md)**：这个开关归它管。决定 1 的「在跑的不受影响」现在有了第三句：**排队中的被抽掉**。决定 3 的露面条件按 ADR-0053 的规则兑现（记录，不是在飞数），那两篇都点名说还差一格——补上了。
- **[ADR-0053](./0053-every-dispatch-is-a-task.md)**：「有记录 ⇒ 生命周期面在模型面前」这条规则落地到 `src/index.ts` 的 active 集合上；本篇把那篇自己记下的缺口补掉。
- **[ADR-0056](./0056-admission-queues-instead-of-rejecting.md)**：决定 7（前台中止抽掉排队中的请求）保留并被验证；§"遗留" 的两条（「模型面主动取消一个排队中的任务」与「`/ptc off` 的截断语义」）都落在本篇。状态机从七态不变，但 `queued -> canceled` 这一行现在有两个来路：前台中止与模型 stop。

## Reopen triggers

- **队列被证明需要界**（一次会话排出成百上千个任务）——那时要回答的是「满了先丢哪一个」，而丢哪一个与「模型能不能撤回自己排的那一个」是两个问题，不是一条。
- **模型开始频繁地把「排队中」与「运行中」搞混**——那时的修法是状态词汇本身（多一个词，或者把 `queued` 折叠掉），不是取消语义。
- **有人要求「取消」也能停掉正在跑的**——那是一个 kill 开关，不是这一条；ADR-0022 的 `ptc_task_stop` 已经是那条路，用户也可以直接用它停。
