| 调用              | query                              | count | need_content | 结果数 | summary 长度（最小–最大） | summary 中位 | 正文总字符 | **现状模型可见字符** | ≈token |
| ----------------- | ---------------------------------- | ----- | ------------ | ------ | ------------------------- | ------------ | ---------- | -------------------- | ------ |
| `chinese-pricing` | DeepSeek 搜索 API 计费 单价        | 10    | 否           | 10     | 191–793                   | 493          | —          | **6,582**            | 1,645  |

## 2. 官方口径被实测推翻了一半

官方文档说 `summary` "通常 600～800 字符"（typically）。实测：

| 调用              | 超过 800 字符的结果数 |
| ----------------- | --------------------- |
| `chinese-pricing` | 0 / 10                |
| `chinese-docs`    | **9 / 10**            |
| `english-docs`    | **9 / 10**            |
| `with-content`    | 2 / 5                 |

最长的一条 **4,757 字符**，是官方口径的 6 倍。

⇒ **"typically" 不是上限。** 任何按 600–800 设计的东西（预算、截断点、上下文估算）都是**按一个不存在的保证在设计**。
本仓的规格（spec 0044 D8）与使用页当时都写着「summary（600–800 字符）」——**那句话是抄官方口径的，不是实测的**。

## 3. 长 summary 是整页摘录，不是「主题句 + 细节」

`chinese-docs` 里一条 2,406 字符的 summary，头尾各 300 字符：

```
头：Search \/ Fetch API 已上线，使用自研搜索引擎，支持网页搜索与抓取，点此查看使用指南。
    # 网页搜索与抓取
    Search 接口和 Fetch 接口为 Agent 与 RAG 应用提供实时网页内容：
    - Search 接口按 query 搜索网页，返回结构化结果。…
    两者都是原始 JSON API，使用与 DeepSeek API 相同的 Bearer 鉴权。
    Base URL 为https://api.deepseek.com：…

尾：…g:zh,en。 after: | DeepSeek after:2025 或 DeepSeek after:2025-01-01 | 将结果限制在指定日期之后发布的网页。
    before: | DeepSeek before:2026 或 DeepSeek before:2026-06-01 | …
    例如： … DeepSeek 模型 site:github.com OR site:huggingface.co lang:zh after:2025", ...
    ### 响应
    请求成功时返回 HTTP 200 与results 数组。搜索正常…
```

`english-docs` 那条 3,267 字符的是一段代码。**两���都是页面的 markdown 摘录**。

⇒ **「摘要」是引擎对整页的压缩摘录，事实散落在任何位置**（官方页面的计费表在长 summary 的**中段**）。
⇒ **按字符截断会静默切掉事实**：截到 800 字符，模型拿到的是页面开头的一截（导航、API 表头），
而**它以为自己读过了这一页**。**丢**是可见的（少了一条结果），**切**是不可见的（事实没了，页面还在）。

## 4. pi 不截断扩展工具的结果

`node_modules/@earendil-works/pi-coding-agent` 里只有 **bash** 工具的输出有截断
（`dist/core/tools/bash.js` + `truncate.js`，并把全文落到 temp file）。扩展工具自己返回的 `content` 块
**原样进模型**。

⇒ **上限只能由本模块给，或者由模型自己的 `count` / `need_content` 给。**

## 5. 上下文能装几次（128k 上下文 ≈ 520,000 字符）

| 场景              | 无界时能装几次 | P1（8k 预算）能装几次 |
| ----------------- | -------------- | --------------------- |
| `chinese-pricing` | 75             | 75                    |
| `chinese-docs`    | **19**         | **64**                |
| `english-docs`    | **16**         | **61**                |
| `with-content`    | 33             | **63**                |

⇒ 现状下，**一个 128k 上下文的子会话做 16～19 次这样的搜索就被检索结果吃满**，
而它自己的推理与工具输出被挤到压缩区。
（这与 ADR-0049 里写的「上下文先于配额用完」方向一致，但**量级比当时按 6–8k 字符估的更狠**。）

## 6. 预算扫描：P1（按排名整条丢弃）能保住几条

P1 = top-k **前缀**（整条结果，不切），超出预算的结果整条丢弃并告知。

| 场景              | 2k   | 4k   | 8k    | 12k   | 16k   | 24k   | 32k   |
| ----------------- | ---- | ---- | ----- | ----- | ----- | ----- | ----- |
| `chinese-pricing` | 3 条 | 5 条 | 10 条 | 10 条 | 10 条 | 10 条 | 10 条 |
| `chinese-docs`    | 1 条 | 1 条 | 3 条  | 4 条  | 5 条  | 9 条  | 10 条 |
| `english-docs`    | 1 条 | 1 条 | 2 条  | 2 条  | 4 条  | 7 条  | 10 条 |
| `with-content`    | 1 条 | 1 条 | 2 条  | 3 条  | 5 条  | 5 条  | 5 条  |

**这张表是本次测量的核心结论**：

- 8k 预算下，长摘要的查询**只保住 2–3 条**（模型要的是 10 条）；
- 要保住全部 10 条，预算得给到 **32k**——**那就是无界的代价**；
- ⇒ **没有一个预算既小又不丢**：数据本身就是 26–31k。界只能选「少给几条」或「切碎页面」。

## 7. 两种「切法」的差别

| 策略                            | 8k 下的结果数 | 每条是否完整 | 模型知不知道自己少了东西  |
| ------------------------------- | ------------- | ------------ | ------------------------- |
| P0 无界（现状）                 | 10            | 完整         | 否                        |
| P1 按排名整条丢弃（top-k 前缀） | **2–3**       | 完整         | **是**（告知 + url 列表） |
| P2 按比例切（每条都切到配额）   | 10            | **全部被切** | 只标了「已截断」          |
| P3 只给 summary，永不给正文     | 10            | 完整         | 否（正文不可得）          |

P2 保住 10 条看着更好，**但那 10 条全部被切过**——被切掉的事实不会有人提起，
而 P1 保住 2–3 条时模型**确切知道自己少了什么、并且能按 url 单独抓回来**。

## 8. 告知语本身有开销

P1 的诚实成本：

| 场景           | 丢几条 | 告知语字符 |
| -------------- | ------ | ---------- |
| `chinese-docs` | 7      | **984**    |
| `english-docs` | 8      | **1,131**  |
| `with-content` | 3      | 435        |

⇒ 告知语要列 url，8 条就是 1,131 字符。**它不在预算内**（预算约束的是结果本体），
原型把两个数分开报，就是为了不让这个开销被藏起来。**告知语的列表长度需要另一个上限**（例如列前 5 条 + 「还有 N 条」）。

## 9. ⚠️ 补测：`snippet`（DeepSeek 自己的短摘要）—— 上次漏测的那个字段

第一次测量只记了 `summary`，**漏了 `snippet`**。补测之后，这条比前面所有结论都重要。

官方字段表里有两个摘要字段：

| 字段      | 官方口径                                   | 实测长度      |
| --------- | ------------------------------------------ | ------------- |
| `snippet` | 短摘要，**与 query 相关**，100～200 字符   | **105–414**   |
| `summary` | 长摘要，通常 600～800 字符，**给模型阅读** | **191–4,757** |

`summary` 的官方描述写着「适用于给模型阅读」——**而实测它是整页摘录**（§3）。
`snippet` 写着「适用于前端展现」——**而实测它恰恰是给模型用的那一份**（见下面的样本）。

### 9.1 每次搜索的模型可见字符：四种做法

| 场景              | 全量 `summary` | P1 整条丢（8k） | P2 按比例切（8k） | **P4 用 `snippet`** |
| ----------------- | -------------- | --------------- | ----------------- | ------------------- |
| `chinese-pricing` | 6,914          | 6,914           | 6,957             | **3,180**           |
| `chinese-docs`    | 26,150         | 8,039           | 7,996             | **3,890**           |
| `english-docs`    | 31,350         | 8,422           | 7,996             | **4,684**           |
| `with-content`    | 15,584         | 8,228           | 8,004             | **1,622**           |

**128k 上下文（≈520,000 字符）能装几次搜索：**

| 场景              | 全量 `summary` | P1 整条丢（8k） | **P4 用 `snippet`** |
| ----------------- | -------------- | --------------- | ------------------- |
| `chinese-pricing` | 75             | 75              | **163**             |
| `chinese-docs`    | 19             | 64              | **133**             |
| `english-docs`    | 16             | 61              | **111**             |
| `with-content`    | 33             | 63              | **320**             |

⇒ **P4 比现状便宜 3–10 倍，比 P1 还便宜 2–4 倍，而且不丢任何东西**——
`snippet` 是 DeepSeek 自己算的摘要，**不是我们的截断**，所以「切会静默丢事实」这条对它不成立。

### 9.2 样本：`snippet` 往往直接含答案，而 `summary` 是页面元数据

```
[chinese-pricing] title: DeepSeek API 已支持网页搜索和抓取，单价为每 1000 次成功请求 5 元
   snippet(154): IT之家 10 月 18 日消息，DeepSeek 今日发布公告，DeepSeek API 现已支持网页搜索与抓取，
                  按请求次数计费，单价为每 1000 次成功请求 5 元 ...
   summary(458): # DeepSeek API 已支持网页搜索和抓取，单价为每 1000 次成功请求 5 元

                  2026-10-18 19:59 IT之家 - 浩渺
                  ...
                  IT之家 10 月 18 日消息，DeepSeek 今日发布公告，…（整页摘录）

[with-content]  title: DeepSeek 搜索 API 正式开放：每千次请求 $0.75，开发者如何接入？
   snippet(136): 定价为每千次成功请求 $0.75 ... Search 和 Fetch 均为 $0.75 / 千次成功请求
                  （来源：DeepSeek 官方定价文档，2026 年 10 月） ... 每千次成功请求（HTTP 200 且有结果）计费 $0.75
   summary(984): # DeepSeek 搜索 API 正式开放：每千次请求 $0.75，开发者如何接入？

                  发布日期：2026-10-19 | 话题：DeepSeek 搜索 API / AI 搜索工具 / RAG 开发
                  ...（整页摘录）
```

⇒ **两条 snippet 都直接含着答案（单价、计费口径），两条 summary 都是页面元数据开头。**
⇒ **我们一直在给模型错的字段**：给了 `summary`（=整页摘录），而 DeepSeek 自己给模型用的短摘要是 `snippet`。

## 10. 测量过程中被自检抓到的三个真 bug（都在原型里，已修）

1. **预算算少了 ~22 字符/条**（`url:` 行、`authority=` 行、字段标签没算进去）——"8000 的预算"实际产出 8,226。
2. **P1 在预算小于第一条结果时返回空结果集**——模型问了个问题，收到一条"有页面没放进来"的告知，却一个页面也没看到。
   ⇒ 加了地板：**第一条永远给**。
3. **告知语少报了**：按前缀丢一条就 break，后面 7 条也没了，告知语却说"还有 1 条"——
   **恰好在需要诚实的地方不诚实**。⇒ 改成把整条尾巴都算进"没放进来"。

这三个都不是读代码能发现的，是**把原型跑起来并断言不变量**才暴露的。
