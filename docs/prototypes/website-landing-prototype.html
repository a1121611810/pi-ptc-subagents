pi‑ptc‑subagents

pi ships no sub‑agents. This is the package that adds them.

Programmable tool calling and subagent fan‑out for pi. The model writes a JS/TS program that composes pi's tools, or fans out to a fresh pi subprocess per task — one round trip instead of many.

pi install npm:pi-ptc-subagents

pi reads the pi.extensions manifest — installed and on for the next startup. No postinstall hook, no extra setup.

One package, two capabilities

01  Programmable tool calling

ptc_run_code / ptc_workflow run a JS/TS program in a worker. It reaches the session's tools as tools.<name>(args). Only the program's return value and its logs come back to the model.

02  Subagent fan‑out

The pi.dispatch binding spawns a fresh pi subprocess per call, so each task gets its own context. Foreground await, or background with a lifecycle you can list, read and stop.

ptc_task_list
  ├─ t-3  audit the render path    running · 41s
  ├─ t-4  check the ADR links      running · 12s
  └─ t-2  verify-dist gate         done · exit 1

What pi deliberately doesn't build

pi's core stays minimal. This is the package that fills the gaps.

pi's own landing page lists what it left out. Three of those gaps are what this package is for — the other three it composes with rather than replaces.

No sub‑agents

→ fan‑out, in‑process or background

pi.dispatch plus ptc_task_*. Session‑level isolation without inventing a task state machine.

No plan mode

→ program the plan instead

Loops, branches and fan‑out live in JavaScript, where the model can express them — not in a second tool protocol.

No background bash

→ long‑lived, inspectable

Background dispatch hands back a handle, not a tmux pane. List it, read it, stop it.

The three things worth knowing

Bindings mirror your loadout

Only tools pi has enabled are reachable from inside a program. A session started with --tools read,bash can only bind those two.

Programs run as you

No OS‑level sandbox. There is an explicit trust posture page, and it is worth reading before you install.

Source is the truth

Public repo, one maintainer. dist/ on npm is the compiled form of what you read.

Read this before installing: tool calls made from inside a PTC program execute directly and bypass pi's tool_call hooks — permission gates and path guards included. Do not rely on those guards while this extension is enabled.

Questions

Is this a different agent from pi?

No. It is a pi extension. It registers tools in the session you already have; it does not run its own agent, and it does not replace pi's codemode when that is present.

Why is the surface detected instead of configured?

Because a mirror of pi's own rule is a second implementation of a rule the host owns — and it goes stale the moment pi changes the rule. Reading pi's real active tool set at session start cannot disagree with pi.

Can I keep it out of my sessions entirely?

Yes — pi config and disable its extensions there. Per‑session, /ptc off turns PTC mode off while keeping the task lifecycle visible.

What happens to long output?

It follows pi's own truncation contract: the text block keeps the tail, the untruncated text is written to a temp file the next program can read, and the collapsed row says truncated.

a PTC program — one round trip, not twelve
// read many files, then keep only the ones that match
const results = await Promise.allSettled(
  paths.map((p) => tools.read({ path: p }))
);

const hits = results
  .filter((r) => r.status === "fulfilled")
  .map((r) => r.value.content[0].text)
  .filter((t) => t.includes("AssistantMessageComponent"));

// and fan out work that does not belong in this context
const audit = await tools["pi.dispatch"]({
  agent: "auditor",
  task: "check every relative link in docs/**",
  background: true,
});

return { matched: hits.length, of: paths.length, audit: audit.id };

Surface detection

Which model-facing tools this package registers, independent of PTC mode. Detected, not configured.

There is no key for the surface mode, and the former surfaceMode setting in ptc.json was removed on 2026‑10‑10. The session names the outcome at startup rather than defaulting in silence, because a detection that cannot be seen is indistinguishable from a pi that moved its dist.

The three questions

  • Does this pi ship a codemode extension directory?
  • Will pi actually load it? Since 0.99.0 a user can disable a built‑in extension, so a pi can ship codemode and be told not to run it.
  • Will codemode be active — callable by the model?

Shipped, loading and active resolves to subagents. Any other combination resolves to full — and so does a probe that cannot answer, which lands in the safe direction.

The surface you get

Surfaceptc_subagentptc_run_code / ptc_workflow
subagents — codemode is present and activedeclaredregistered, reachable from a codemode script
full — everything elsenot registereddeclared to the model

The asymmetry is deliberate. On the subagents line the program pair is registered, which is what lets a QuickJS sandbox reach pi.dispatch — something it cannot do on its own.

Forcing the subagents surface

Put codemode in your tool list:

pi --tools read,bash,edit,write,codemode

or in settings:

{ "defaultTools": ["read", "bash", "edit", "write", "+codemode"] }

The full detection table, startup notices, and edge cases (--print, --no-extensions, untrusted projects) live in the repository at docs/usage/surface.md.
