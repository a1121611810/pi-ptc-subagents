问题：一次搜索的模型可见文本应该有界吗？界在哪？按什么切？ —— 数据全部来自 2026-10-20 对真实 Search API 的四次调用（本页内嵌，无模拟）。

实测：一次 count=10 的搜索，模型可见文本有多大

文档说的「summary 通常 600–800 字符」在真实查询上不成立。 四次真实调用里有两次，10 条结果里 9 条超过 800 字符，最长 4,757（中位数 2,401 / 3,267）。 官方口径是 "typically"，不是上限——把它当上限来设计，就是按一个不存在的保证在设计。
pi 不截断扩展工具的结果（只截断 bash 的输出，落到 temp file）。 ⇒ 上限只能由本模块给，或者由模型自己的 count / need_content 给。

            所以按字符截断会静默切掉事实。
            官方页面的计费表在长 summary 的中段；截到 800 字符，模型拿到的是页面开头的一截
            （导航、API 表头），而它以为自己读过了这一页。
            ⇒ 「切」比「丢」更危险：丢是可见的（少了一条结果），切是不可见的（事实没了，页面还在）。
          

          

            这正是 P1（按排名整条丢弃）存在的理由：丢掉的是整页，而模型仍然可以用它的 url
            单独抓回来——前提是工具告诉它丢了哪几条。

            规则：按 DeepSeek 的排名顺序，整条放入结果，直到预算用完；放不下的整条不放，
            并在文本末尾告知丢了哪几条、可以按 url 单独抓。
          

          

          

          

            为什么「按排名」而不是「按字符」：排名是 DeepSeek 给的相关性信号（rerank_score / authority），
            尾部的结果本来就是低相关的那些；丢掉低相关的整页，比切碎高相关页的前 800 字符更划算。
