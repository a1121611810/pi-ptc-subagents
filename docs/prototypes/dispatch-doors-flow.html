派发与路由 · 全景

模型只调「建任务」，派发降为内部实现。模型面前不再出现 dispatch 这个词—— 入口是 pi_task_ptc / pi_task_codemode，背后是任务侧： 建一条任务记录 → 派发（内部实现）→ 按参数决定等不等； 并发满了不拒绝，排队等（照 libuv 的线程池）。 registry 是派发的唯一痕迹，lifecycle face 是它唯一的模型面。 前台和后台不再是两个机制——是一条路径上的一个参数。
代码拆成四个核心子项目：入口（模型面：两扇门 + route registry + section/会话注入）· ptc（编排器：ptc_run_code / ptc_workflow、worker pool、严格模式）· dispatch（任务引擎：闸门、taskId、registry、libuv 队列与槽、spawn、落盘、报告收集）· task（任务面：lifecycle face——ptc_task_list / ptc_task_output / ptc_task_stop，读/停 sub 的 registry）。 依赖单向：入口 → dispatch、ptc → dispatch、task → dispatch——dispatch 持全部任务状态，其余三个只是它的调用方。 这一页把十节放在一起，决策已全部走完（30 条）。

一 统一后的全景：每个派发都是一条任务

今天前台派发是纯内存的（不铸 task id、不进 registry、产出只在内存里），后台才进——所以「派发」和「任务」是两件事。 统一之后：门背后先建记录再起进程，前台 = 建 + 等终态，后台 = 建 + 立即返回。 于是 registry 是派发的唯一痕迹，lifecycle face 是它唯一的模型面。

宽松模式的两处实测代价

2026-10-21 订正（实现票 #244 在 base commit 上复测）：本页原写的两个「实测后果」被复测推翻了一处、收窄了一处—— 机制是真的，但当时那两条的后果被说大了。下面两栏是订正后的实测事实；决策本身（强制严格）不变，理由仍然是「与上游 DSH 对齐」。
代价一 · 隐式全局真的被建出来

宽松模式下赋未声明变量 → 建在 globalThis 上，这一点是实测的（own enumerable property，值 42）。 而 worker pool 确实复用 worker（worker-pool.ts：warm worker 服务多次 run）。 但：旧 ADR-0017 的 startRun / restoreWarmBaseline 会在下一次 run 之前把隐式全局删掉， 所以今天它不会污染到下一段程序——实测同一 worker 内连跑两段，run 2 读到的是 undefined。

// 同一个 worker 上下文里连跑两个程序（base commit 实测） run 1: leaked = "我是 run 1 漏下的" → 成功（全局真的建出来了：own: true, value 42） run 2: 读得到吗 → 读不到（warm-baseline 恢复已经把它删了）

严格模式把「事后被清掉」变成「从不创建」——清理原本由另一个机制承担， 而那个机制一旦漏跑，污染就会回来。

代价二 · 静默的是「写」，不是「读」

原页写的是「results 漏成 result → 模型拿到 undefined，零错误信号」。 这一半不成立：读一个未声明的名字在宽松模式下本来就是 ReferenceError（实测 return results; → results is not defined）。 真正静默的是写那一侧——给拼错的名字赋值会悄悄建一个全局。

// 宽松模式实测 return results; → ReferenceError（读：本来就响） results = 1; → 成功（写：静默建全局，零错误信号）

严格模式让写这一侧也变响（ReferenceError）， 这才是 docs/testing-constraints.md 第 3 条「不留静默失败」在程序语言层的落实。 属性名打错（obj.results）两种模式都静默——那不在严格模式的射程内。

决定：强制严格（改一行）

// packages/ptc/src/runtime/worker-main.ts:458 - return new Function(`${source}\nreturn ${programName}();`); + return new Function(`"use strict";\n${source}\nreturn ${programName}();`);
为什么理由
这是对不齐，不是偏好上游 DSH 明确严格。我们不跟，就是跟已记录的上游分叉
我们跑的是 TypeScriptTS 编译成 module 时默认 alwaysStrict；用 stripTypeScriptTypes 等于静默丢掉了 TS 默认的严格性。模型（和用户）写 TS 时预期的就是严格语义
隐式全局不再被创建 + 写侧的手滑变响上面两处实测事实。严格模式一次解决两个——代价一不再是「事后靠另一个机制清掉」，代价二从「只有写侧静默」变成读写都响
用户自带 "use strict"; 不冲突实测：外层加 strict 后，用户那行仍然合法（strict 里再声明是 no-op），不报错
代价（要认下来）：
① 破坏性变更：依赖宽松语义的现有程序会开始报错——顶层 this 从 globalThis 变 undefined、隐式全局变 ReferenceError、重复参数变编译期 SyntaxError、八进制字面量变 SyntaxError。
② 错误路径多一类（编译期 SyntaxError）。
③ 程序内无法 opt out——JS 没有 "use sloppy" 这个指令，所以严格化是单向的。
归入本轮那个大 breaking release（门改名 + surface 改名 + 严格模式一起发）。
顺带（同一块地，别混）：parity audit 的 A8「原型污染加固」我们也没有（grep intrinsics / Object.create(null) 命中 0）—— 严格模式不解决原型污染（那要靠 A8 那套），但它少一类「往全局乱写」的事故。两件事得分开做。
