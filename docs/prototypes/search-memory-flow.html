搜索记忆 F5：抓一次免费复用，只对"搜索来的亲戚"成立

场景：子代理里的 web_ds_search，配额 30 次/进程（烧完锁死）。记忆的设计意图是抓一次、之后免费 serve——但门槛藏在 storeText 里。

① 正常路径：URL 来自搜索结果 设计意图 ✓ 兑现

# 第 1 步：search —— 建一条记忆条目 search("pi config 文档") ──► 发请求 ──► 记忆条目#3 建好： query + 结果列表 [url-A, url-B, url-C] 配额 30 → 29 # 第 2 步：open 结果里的 URL —— 正文有地方存 open(url-A) ──► 发请求抓正文 ──► storeText：在条目#3 的结果列表里找到 url-A ✓ 是亲戚 ──► 存进 条目#3.textByUrl[url-A] ✓ 入库 配额 29 → 28 # 第 3 步：find 同一页 —— 记忆命中，免费 find(url-A, "model.*=") ──► lookup：遍历条目的 textByUrl ✓ 命中 ──► 页内正则匹配 ──► 返回行 不发请求 ✓ 不烧配额 ✓ 仍是 28

这条路径里"抓一次免费复用"是成立的——因为 URL 先当了搜索结果，storeText 能在条目的结果列表里找到它。

② F5 病径：直接 open 已知的 URL 正文被丢 · 烧两次

# 第 1 步：open 一个模型早就知道的 URL（没搜过） open(https://pi.dev/docs/config) ──► 发请求抓正文 ──► storeText：遍历 5 个搜索条目的结果列表… 没有这个 URL ✗ 不是亲戚 ──► 正文被静默丢弃（函数直接 return，什么都没存） 配额 30 → 29（钱花了，货没存） # 第 2 步：find 同一页 —— 记忆里没有 find(同 URL, "timeout") ──► lookup：5 个条目的 textByUrl 全 miss ✗ ──► 重新发请求抓整页 ──► 再存（还是被丢） 配额 29 → 28 同一个页面烧了两次配额；接口注释承诺的 "后续 find/open 免费 serve" 在这条路径上兑现不了。

孩子的典型用法恰恰是这条：模型盯着某个已知文档/仓库 URL 干活，search 根本不出场——F5 烧的就是最高频的路径。

记忆结构：为什么"非亲戚"URL 没有家

createSearchMemory()
├─ entries[]                       ← 最多 5 条（SEARCH_MEMORY_MAX_ENTRIES）
│   ├─ query: "pi config 文档"
│   ├─ matches: [ {url, title, snippet}, … ]   ← search 的结果列表
│   └─ textByUrl: Map<url, 正文>               ← 只有"出现在 matches 里的 url"才存得进来
│                                                  （storeText 先按 matches 找门，找不到就 return）
└─ 总预算 400K 字符（SEARCH_MEMORY_MAX_CHARS），超出淘汰最老条目

病根一句话：textByUrl 挂在搜索条目下面，正文必须先进搜索结果的门，才配被记忆。直接 open 的 URL 没有条目可挂，无家可归。

修法（约 10 行，F5）：加一个独立兜底桶 looseTexts: Map<url, 正文>——不挂在任何搜索条目下；storeText 找不到亲戚时存这里，lookup 两个桶都查；共用同一个 400K 预算和淘汰逻辑。改完两条路径都兑现"抓一次免费复用"。
