# search-context-budget — 结论

**日期**：2026-10-20
**问题**：一次搜索的模型可见文本应该**有界**吗？界在哪？按什么切？
**数据**：`docs/prototypes/search-context-budget-measurements.md`（四次真实 API 调用）
**原型**：`docs/prototypes/search-context-budget.html`（一次性，内嵌真实数据，双击即开）

---

## TL;DR

**要设界，但「界」不是钱的问题，是上下文的问题；而且没有一个既小又不丢的界。**

- 一次 `count=10` 的搜索，模型可见文本 **6,582–31,020 字符（1,645–7,755 tokens）**。
  官方口径「summary 通常 600–800 字符」在真实查询上**不成立**（10 条里 9 条超 800，最长 4,757）。
- 128k 上下文的子会话，**现状下只装得下 16–19 次**这样的搜索。
  ⇒ 界必须给，而且**只能是模块给**（pi 只截断 bash 的输出，扩展工具的结果原样进模型）。
- **不能按字符切**：`summary` 是**整页摘录**，事实散落在任何位置（官方计费表就在长 summary 的中段）。
  切 = 静默丢事实，而模型以为自己读过了这一页。**丢**是可见的，**切**是不可见的。
- **按排名整条丢弃（top-k 前缀）+ 明确告知丢了哪些、可以按 url 补抓**——这是唯一不撒谎的切法。
- **但代价是实的**：8k 预算下只保住 **2–3 条**（模型要的是 10 条）；要保住全部 10 条，预算得给到 32k，
  **那就是无界的代价**。⇒ **「界定多大」是一个必须由人拍板的取舍，不是能算出来的最优解。**

## 1. 三个被实测推翻的「想当然」

| 想当然                                       | 实测                                                                                 |
| -------------------------------------------- | ------------------------------------------------------------------------------------ |
| 「summary 大概 600–800 字符」                | 10 条里 **9 条超 800**，最长 **4,757**（中位 2,401 / 3,267）                         |
| 「一次搜索大概 6–8k 字符」（本仓此前的估算） | 最高 **31,020 字符**（≈7,755 tokens），是估算的 4 倍                                 |
| 「截短一点，模型自己会读剩下的」             | 长 summary 是**整页摘录**，截到 800 字符留下的是页面开头的一截，事实（中段）在另一头 |

⇒ **spec 0044 D8 与 `docs/usage/web-ds-search.md` 里那句「summary（600–800 字符）」是抄官方口径的，不是实测的**，
现在应当改成实测分布，或者干脆只写「典型 200–4,800」。

## 2. 这个界是上下文界，不是钱界

- 钱：5 元/千次成功请求 ⇒ 20 次搜索 ≈ **0.1 元**。不是问题。
- 上下文：现状下 16–19 次搜索吃满 128k。**是问题**。
- ⇒ 配额（`maxCallsPerSession`，按次数）**管不住上下文**——100 次 × 31k ≫ 任何会话的窗口。
  两者是不同的轴，**要分开说**。

## 3. 为什么是「整条丢弃」而不是「按字符切」

| 策略                      | 8k 下的结果数 | 每条完整？ | 模型知道自己少了什么？ |
| ------------------------- | ------------- | ---------- | ---------------------- |
| P0 无界（现状）           | 10            | 完整       | 否                     |
| **P1 整条丢弃 + 告知**    | **2–3**       | 完整       | **是**                 |
| P2 按比例切               | 10            | **全被切** | 只标了「已截断」       |
| P3 只给 summary，不给正文 | 10            | 完整       | 否（正文拿不到）       |

P2 看着更好（条数多），**但那 10 条全部被切过**；被切掉的事实没人提起，模型无从察觉。
P1 保住 2–3 条，模型**确切知道少了 7–8 条、并且能按 url 单独抓回来**。

⇒ **代价换的是诚实，不是效果。** 这个取舍成立的前提是：模型**能**用 url 补抓（它有 `url` 参数，一次一页）。

## 4. 「界定多大」——这是需要人拍板的地方

P1 保住几条 vs 预算（实测）：

| 预算     | `chinese-docs` | `english-docs` | `with-content` |
| -------- | -------------- | -------------- | -------------- |
| 2k / 4k  | 1 条           | 1 条           | 1 条           |
| **8k**   | **3 条**       | **2 条**       | **2 条**       |
| 12k      | 4 条           | 2 条           | 3 条           |
| 16k      | 5 条           | 4 条           | 5 条           |
| 24k      | 9 条           | 7 条           | 5 条           |
| 32k      | 10 条          | 10 条          | 5 条           |
| （无界） | 10 条 / 26.2k  | 10 条 / 31.4k  | 5 条 / 15.6k   |

**没有「既小又不丢」的界**：数据本身就是 26–31k，界只能选「少给几条」或「切碎页面」。

⇒ 三个数要人来定：

1. **界多大？** 8k（≈2,000 tokens，占 128k 的 1.6%）保住 2–3 条；16k 保住 4–5 条；24k 保住 7–9 条。
2. **是固定常数，还是可配？** 现有 `webDsSearch` 已经有 `enabled` + `maxCallsPerSession`；
   再加第三个键（`maxChars`）是第三个旋钮。**倾向先做固定常数**——它不是用户会天天调的东西，
   而每次多一个旋钮就多一份「调了之后行为变成什么样」的说明义务。
3. **告知语的列表上限？** 丢 8 条时告知语是 **1,131 字符**（列出全部 url）。
   应当只列前几条 + 「还有 N 条」——**这个上限本身也要定**（5 条？3 条？）。

## 4.5 ⚠️ 补测带来的转向：概览用 `snippet`，别用 `summary`

第一次测量**漏了 `snippet` 这个字段**（`docs/prototypes/search-context-budget-measurements.md` §9）。补测之后，
**本记录 §3 的推荐（P1 整条丢弃）不再是最优解**，理由有三条：

1. **`summary` 是整页摘录，`snippet` 是 DeepSeek 自己算的短摘要**（官方说 `snippet`「适用于前端展现」——
   实测它恰恰是给模型用的那一份，两条样本里**都直接含答案**）。**我们一直在给模型错的字段。**
2. **用 `snippet` 做概览便宜 3–10 倍，且不丢东西**（每跳 6.4k–31.4k → **1.4k–4.7k**；128k 能装的搜索次数
   **16–20 次 → 111–320 次**）。它是 DeepSeek 自己算的摘要，**不是我们的截断**，
   所以 §3 的核心结论「切会静默丢事实」**对它不成立**。
3. ⇒ **P1 那套「丢整页 + 长告知语」也就没必要了**（P1@8k 要 8.0k–8.4k，P4 只要 1.6k–4.7k，
   而且 P1 还要额外花 435–1,131 字符的告知语）。

⇒ **推荐的形状变成：概览 = title + url + authority/rerank/date + `snippet`；深度 = 按需取。**
**「按需取」有三条路**（见 §5）。

## 4.6 ⚠️ 联网查证：业界四种做法，没有一家把结果集塞进上下文

2026-10-20 联网查证（详见 `docs/research/agent-search-result-delivery-patterns-20261020.md`）：

| 做法                                      | 谁                                           | 模型看到什么                                                        | 深度怎么来                                                                                                       |
| ----------------------------------------- | -------------------------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| 结果块只给 title+url，**内容加密**        | Anthropic web search                         | `{url, title, encrypted_content, page_age}` —— **无全文无 snippet** | **模型引用时，服务端注入被引段落**                                                                               |
| 结果集不进上下文，答案带引用，动作可审计  | OpenAI Responses web_search                  | `text` + `annotations[].url_citation`                               | `web_search_call.action` ∈ {search, **open_page**, **find_in_page**}；`search_context_size` 控制多少结果进上下文 |
| **给句柄、不内联字节**                    | MCP `resource_link`                          | `{type:"resource_link", uri, name, mimeType}`                       | 客户端自己去取                                                                                                   |
| 处理完就清掉旧工具结果 / 进上下文前自己筛 | Anthropic context editing、dynamic filtering | —                                                                   | —                                                                                                                |

**共同点：全是「概览 + 按需取」。** 原则原话：「上下文是一种**收益递减的有限资源，不相关的内容会削弱模型的专注度**」。

**⇒ 本仓的落点被坐实了，而且能做得更省**：
Anthropic 的深度是**等服务端在引用点注入**；而**我们的 `summary` 是 API 已经算好、已经付过钱的**
（实测 191–4,757 字符）⇒ **按需取它零额外 API 成本、零额外延迟**。
DeepSeek 原始 API 没有引用注入（已实测），所以本地的等价物就是「概览 + 工具动作取深度」。

**⇒ 落地文件这个中间方案可以不要了**：工具自带 `open_page` / `find_in_page` 两个动作
（对标 OpenAI 的 action 模型）就够，且**不产生临时文件**、**不依赖子代理有 read/bash**。

## 5. 推荐的形状

1. **模块给模型可见文本设一个字符预算**（默认 12,000–16,000 字符 ≈ 3,000–4,000 tokens）。
2. **超预算的结果按 DeepSeek 的排名整条丢弃**（top-k 前缀，**第一条永远给**——预算小于第一条时不能返回空结果集）。
3. **必须告知**：丢了哪几条、它们的 url、以及「可以按 url 单独抓」。
   **告知语是额外开销，不在预算内**（原型把两个数分开报，就是为了不让它被藏起来）。
4. **不按字符截断任何一条摘要。**
5. **正文的取用保持现状**（`need_content` 时整页给），但它同样受总预算约束——
   实测一次 `need_content` 的搜索是 15,402 字符，其中 10,836 是正文。

## 5.5 落地之后 e2e 又抓出两个缺陷（已修）

改形（概览 + 三个动作）之后重跑真机 e2e，**两处都是只有真机跑才会暴露的**：

1. **记忆只留最后一次搜索 ⇒ 模型白花一次请求。** 子代理搜了三次才去 `open`，而它打开的是**第一次**搜索里找到的那一页。那次 `open` 于是退回成抓取——**模型为了一段 API 早就算好、早就计过费的文字付了一次请求**。⇒ 记忆改成跨**最近 5 次搜索**（按 url 合并）+ 字符上限。
2. **模型不逐字节照抄 url。** 它去掉结尾的 `/`、带 `#1` 片段、带跟踪 query。⇒ 宽松匹配：**scheme+host 相同、path 去尾 `/` 后相同、fragment 不计、query 相同或「记住的那条本来没有 query」**；只有 query 不同的两条**不算同一页**（否则会拿到错的内容）。

**两条都补了单测**（`tests/web-ds-search.test.ts`），e2e 也加了两条断言：「它真的再问了」（调用参数里有 `open` 且是它搜到的 url）与「那一次再问没有花钱」（工具结果里写着「来自上一次搜索的结果」）。

## 6. 没验的

- **没有在真机上跑过「设了界之后」的行为**：本轮的 e2e 跑的是**无界**版本。
  界一旦加上，**「模型拿到被告知的结果集，还能不能答对」需要重跑一次 e2e**——
  这是实现之后必须补的一步，不是这次能顺带验掉的。
- **没有测「模型会不会真的按告知语去补抓」**（告知语说「可以按 url 单独抓」，模型会不会照做）。
  这需要一次带 follow-up 调用的真机跑法。
- **`count` 的分布没有采样**：四次调用的 query 是我挑的，真实工作负载的 query 长度/类型分布未知。
  结论「summary 通常远超 800 字符」在这四个 query 上成立，**在更广的 query 分布上还只是四个样本**。

## 7. 复现

```bash
node docs/prototypes/search-context-budget-measure.js   # 重新取数（要凭据 + 网络 + 花钱）
node docs/prototypes/search-context-budget-check.js      # 验原型的逻辑与不变量
open docs/prototypes/search-context-budget.html          # 自由试验：换场景、换策略、拖预算
```

自检脚本断言的五条不变量（全部绿）：

1. 原型的内联脚本能跑（没有 id 写错、没有引用错误）；
2. P1 的**结果本体**不超预算（地板那条除外，且必须只地板那一条）；
3. P1 给出的是 **top-k、每条完整**，不是切碎的版本；
4. 告知语**把整条没放下来的尾巴都算进去**，并列出每一条的 url；
5. P2 切过的地方**在文本里标了出来**。

> 原型是**一次性**的：它的价值是上面这些数字和结论，不是那份 HTML。
> 实现期只应保留 §5 的决策，**原型本身不进 main**（按仓库惯例：留在一次性分支上，并在实现票里留一个指针）。
