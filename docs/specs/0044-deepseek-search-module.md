# Spec — 内置 DeepSeek 搜索模块：一个门禁化的、只活在被派出的子代理里的检索能力

Map: [#226](https://github.com/a1121611810/pi-ptc-subagents/issues/226)
Status: **draft** — decisions frozen from the map. 实现者开工前不需要再做任何形状或流程上的决定。

> **本 spec 不写实现代码。** 它把 map #226 的四张决策票（#227 形态、#228 门禁、#229 配额、#233 结果与错误）连同两张已关的研究票（#230 凭据面、#231 codemode 桥接）合成一份可直接实现的规格。
>
> **形状在 2026-10-20 被二次 grill 改写过一次**：从「一个实现、两个程序面、默认不面向模型」改成「**只活在被派出的子代理里，由子代理自己的模型直接调用**」。决策记录见 [ADR-0049](../adr/0049-the-search-lives-in-the-child.md)（现行）与 [ADR-0047](../adr/0047-deepseek-search-is-program-internal.md)（同日撤销）。

## Problem Statement

pi 没有任何网页检索能力：内置工具只有 `read` / `bash` / `edit` / `write` / `grep` / `find` / `ls` 七个，没有 web search，也没有 web fetch。所以一条「查一下 pi 的 codemode 怎么暴露工具」的问题，模型只能靠 `bash` + `curl` 硬凑——而 `bash` 本身在本包是 **opt-in binding**（ADR-0040），默认不暴露。

DeepSeek 官方在 2026-10-17 开放了 Search / Fetch 两个裸 JSON 接口（`POST https://api.deepseek.com/v1/tools/search` 与 `/v1/tools/fetch`），**模型无关**（请求体里没有 `model` 字段），与聊天模型完全解耦；同一把 `api.deepseek.com` 的 Bearer key 即可调用。2026-11-01 起 server 端工具调用路径也按次计费（5 元 / 千次成功请求）。

但「加一个能联网的工具」这件事本身带三个新风险，本 spec 逐个封掉：

1. **网络出口**——一个能往外发请求的工具，天然是 opt-in 能力（`bash` 的先例）。
2. **凭据**——要复用 pi 已配置的 DeepSeek 凭据，而「配了没有」的判定踩在一个真实的坑上（见 D6）。
3. **上下文**——检索结果天然体积大，而本包的主题之一就是把模型直接面收窄。

## Solution

**一个内置 DeepSeek 搜索模块**：DeepSeek Search + Fetch，**一份实现、一个面、三个动作**——**只活在被派出去的子代理里**，在子代理里是**子代理自己的模型**一步就能调的 model-facing 工具；由一个**默认关**的开关 + 一条**凭据判定**双重门禁；带一个 **per-child-process 配额**；**概览 + 按需取深度**，错误文案**面向模型写**。

**三个动作**（一次只做一个）：

| 动作     | 参数                   | 模型拿到什么                                                                 |
| -------- | ---------------------- | ---------------------------------------------------------------------------- |
| `search` | `query`（+ count 等）  | **概览**：每条结果一行块——title / url / 三个阈值 / DeepSeek 自己的 `snippet` |
| `open`   | `open: "<url>"`        | 那一页的**完整 `summary`**（搜索时若要了正文，连正文一起）                   |
| `find`   | `find: {url, pattern}` | 那一页里命中 `pattern` 的**行号**                                            |

**`open` 与 `find` 能从上一次搜索的结果里直接取时，是免费的**——那��段文字 API 早就算好、早就计过费了。

名字里带 `ds`（`web_ds_search` / `webDsSearch`）不是冗余：一来它只走 DeepSeek，二来 DSH 自带一个叫 `web_search` 的工具，而 pi 的工具注册表按名字做 key、同名会互相覆盖——理由见 [ADR-0049](../adr/0049-the-search-lives-in-the-child.md) §命名。

```
      父会话（ptcDepth = 0）                 被派出的子代理（ptcDepth > 0）
   ┌──────────────────────────┐        ┌──────────────────────────────────┐
   │  没有这个工具              │        │  pi 工具 web_ds_search            │
   │  连凭据都不解析            │  ───▶  │  exposure: "direct"               │
   │  到网的唯一路径：           │  dispatch│  子代理的模型一步就能调            │
   │  派一个能搜的子代理         │        │  一次工具调用，没有程序             │
   └──────────────────────────┘        └──────────────────────────────────┘
```

### 1. 形状

| 位置             | 怎么到                                        | 谁能调           | 跳数 |
| ---------------- | --------------------------------------------- | ---------------- | ---- |
| **只在子代理里** | pi 工具 `web_ds_search`，`exposure: "direct"` | 子代理自己的模型 | 1    |
| 父会话           | **不注册**（不在注册表里），也**不解析凭据**  | ——               | ——   |

**判据是 `ptcDepth > 0`**——`dispatch()` 给子进程打的 `PI_PTC_DEPTH`，与 `ptc_child_report` 用的是同一个机制。父会话里这个工具**不存在**（不是「注册了但隐藏」）。

### 2. 门禁

```
开关 webDsSearch.enabled = false  →  任何地方都不注册这个工具
开关 = true  +  有凭据          →  子代理里正常可用
开关 = true  +  无凭据          →  子代理里仍注册，但标注不可用
                                  + 启动告警一次（只在子代理里）
                                  + 调用返回面向模型的可读错误
父会话（无论开关）             →  不注册，也不读凭据文件
```

### 3. 配额

**per child process**——一个子代理是一个完整的 pi 进程，它有一份额度。**默认 30 次**，可配（`0` = 不限）。Search 与 Fetch 共用一个计数器，**只在成功请求时计数**（从上一次搜索结果里直接取的 `open` / `find` **不发请求、不计配额**）。超限不报错，回一句让模型用已有信息继续作答。

**30 是按上下文定的，不是按钱定的**：概览实测 1,505–4,452 字符/次（见 D8），30 次 ≈ 45k–135k 字符，正好是一个 128k 上下文能装的检索结果量。钱不是约束轴（30 次 × 0.005 元 = **0.15 元**），上下文才是。

**诚实的乘数关系**：父会话派出 N 个子代理 ⇒ 整个父会话最坏情况是 N × `maxCallsPerSession` 次成功请求（按官方价格 0.005 元/次 ⇒ **≤ 0.5N 元**，而实际远低于此，理由见 D7）。父侧下发额度来兜住它**按官方价格换算后判定不值得**（见 Out of Scope）。

### 4. 结果与错误

结果**原样透传** DeepSeek 的 10 个字段（结构化载荷里），**模型读到的是概览**，深度按需取，不做引用装配。错误文案是**一份共享常量**，10 个状态码各一句，外加「200 但空数组」这个**非错误信号**各一句。

## User Stories

- **作为子代理的作者**，我希望我派出去的 child 能自己发起检索——因为 child 是完整 pi 进程，扩展在它里面照常加载，而搜索工具**就注册在它里面**（判据是深度，不是配置）。
- **作为子代理里的模型**，我希望搜索是**我自己能调的工具**——因为「这条来源靠不靠谱、够不够新、相不相关」的判断力在干活的那一侧，不该被挪到两跳之外。
- **作为写程序的人**，我希望一次能查多个关键词、并且只把我要的字段回给模型——因为 `count` 拉大不额外计费（计费按请求不按条数），而裁剪是我的事。
- **作为本机的主人**，我希望搜索**默认关**、**只在子代理里**、并且在我没配 DeepSeek 凭据时**明确告诉我缺什么**——因为我不想装个扩展就多一条隐形的联网出口，也不想父会话里凭空多一个联网工具。
- **作为模型**，我希望搜索失败时读到的是一句**我能据此改变策略**的话（该重试 / 该换来源 / 该收工），而不是一个看不懂的状态码。

## Implementation Decisions

### D1 — 搜索只活在被派出的子代理里，在子代理里是 model-facing 顶门

- **只在 `ptcDepth > 0` 时注册。** 判据在 `registerSearchModule` 的**第一行**，在读配置、解析凭据之前。
- **父会话不解析凭据。** 父进程里不持有一把能开网络出口的 key——「没有这个能力」不是「有这个能力但关着」。
- **子代理里 `exposure: "direct"`。** 子代理的模型一步就能调它，一次工具调用。

**为什么不是「顶层 model-facing 工具」（业界默认）**：那会让**父会话**直接拿到联网能力，检索结果也会进父会话的上下文。运营方的方向是「能力给到子代理，让子代理拥有联网查询的能力/工具，这样能减少不确定性，并且耦合性也不会放大」。

**为什么不是「程序内可达的两个面」**（原 ADR-0047 的形状，已撤销）：「模型看不见」从来不是硬保证——`tool_search` 能把 `codemode` 档工具**激活进模型声明**（真机实测，见 `docs/research/pi-codemode-bridge-live-probe-20261020.md`）；而且 0.86.x 上 `exposure` 字段根本不存在（`docs/agents/pi-compat-matrix.md:63`），注册的工具**一律面向模型** ⇒ 旧形状只能留 PTC binding 一条路，代价是 `subagents` surface 绕两跳。详见 [ADR-0049](../adr/0049-the-search-lives-in-the-child.md) §Context。

**硬约束**：**父会话不得注册这个工具，也不得解析 DeepSeek 凭据。**

### D2 — 一份实现，三个动作

一份 HTTP 客户端 + 一个 DeepSeek provider 模块 + 一个 pi 工具，工具的三个动作共用它们。

**为什么是三个动作而不是一个**：`search` 给概览，深度（`open`）与定位（`find`）都是**在已知的一页里再问一次**。三个动作对应 Anthropic / OpenAI / MCP 三家都在用的形状
（`docs/research/agent-search-result-delivery-patterns-20261020.md`）：

- **Anthropic 的 web search（server tool）**：结果块只给 `url` / `title` / `encrypted_content` / `page_age`——**没有全文，也没有 snippet**；模型**引用**某条时，服务端才把被引段落注入上下文。
- **OpenAI Responses 的 `web_search`**：`web_search_call.action` ∈ {`search`, **`open_page`**, **`find_in_page`**}，外加 `search_context_size` 控制多少结果进上下文。
- **MCP 的 `resource_link`**：「返回句柄而不是内联字节」是**协议级**的标准。

**本仓的等价物**：DeepSeek 原始 API **没有引用注入**（已实测：无引用角标、无流式），所以「引用点注入」做不到；但**本仓有一条 DeepSeek 独有的便宜**——**API 已经为每条结果算好了 `summary`**（191–4,757 字符）**并且已经计过费了**。所以深度是**先不给、按需给**，零额外 API 成本、零额外延迟。这比 Anthropic 的做法还省一步（它要等服务端注入）。

**随之消失的**：binding 注入、binding contract 里搜索那条 note、两个 PTC 工具描述里的调用约定段、硬编码的「一份实现两个面」。

### D3 — 命名：名字里带 `ds`

| 位置                 | 名字            |
| -------------------- | --------------- |
| pi 工具              | `web_ds_search` |
| 配置键（`ptc.json`） | `webDsSearch`   |

**两个名字都带 `ds`，这不是冗余，是两处各自需要说清的事。**

1. **一眼看得出这是 DeepSeek 提供的搜索。** 这个能力要 DeepSeek 的 key、走 DeepSeek 的账单、用 DeepSeek 自研的搜索引擎（2026-10-17 起开放，11-01 起 server 端路径也按次计费）。一个叫 `web_search` 的名字会让人以为它是「通用网页搜索」，而它其实**只**走 DeepSeek。
2. **provider 是契约的一部分，不是实现细节。** 基线 6 已经定死**不做可插拔**——检索源固定为 DeepSeek，不预留抽象层。所以「这是 DS 的搜索」是一个**永久**的事实。
3. **⚠️ 与 DSH 自带工具的同名覆盖风险。** DSH 自己就带一个叫 `web_search` 的工具（`dsh-tool-web`），而 pi 的工具注册表是**按名字做 key 的 Map**（`toolRegistry.set(tool.name, tool)`）⇒ **同名注册会互相覆盖**。本仓自己的 `src/mode/ptc-mode.ts` 与 `tests/ptc-mode.test.ts` 也一直拿 `web_search` 当「别的扩展的工具」的例子 ⇒ 这个名字在本仓语境里**已经指 DSH 的工具**了。

pi 工具名走 `--tools` allowlist 匹配，**不带点更安全** ⇒ 工具名用下划线。

**这些是刻意的，不要被「统一名字」或「去掉冗余 ds」的善意改动。**

### D4 — 开关：独立键，默认关

- **位置与形状**：`~/.pi/agent/ptc.json` 新增 `webDsSearch: { "enabled": boolean }`。
- **不并进 `optInBindings`**：那是一个**许可**（"给我这个已知的 pi 内置 binding"，目前只有 `bash`，ADR-0040），fail closed；搜索是**包自有能力**的开关，语义不同 ⇒ **独立键**。
- **默认值 `false`**：网络出口 + 按次计费 + 默认不该改变别人机器的行为 ⇒ 贴 `bash` opt-in 的 fail-closed 家族。**用户必须显式开。**
- **读一次**：扩展加载时读一次（与 `optInBindings` / `whyEnabled` 同纪律）。要改就重载。

### D5 — 缺 key：工具仍注册，但标注不可用 + 启动告警一次

**业界没有完全同形先例**（研究结论：没有 harness 做到「总开关打开 + 缺 key 时既保留工具又只在启动时告警一次」），所以本契约自己写死。三件事同时发生：

1. **标注不可用** — 工具描述里写明「本会话未配置 DeepSeek 凭据，调用会失败」。**两处都要写**：工具的描述（每会话注册一次，那一句说的是这一会话的真话）与**调用失败时抛出的那句**。**两处必须是同一个共享常量**（one-home rule；先例 `BINDING_CONTRACT`，测试断言两边 `toContain(同一常量)`）。
2. **启动告警一次** — `ctx.ui.notify(..., "warning")`（仓库先例：codemode drift 告警，`src/index.ts:880`）。**一次**（once-only latch），不刷屏。**只在子代理里发**——父会话没有这个能力，也就没有可告警的东西。
3. **调用返回面向模型的可读错误** — 文案见 D9。**抛错**，不用 `isError`（0.86.0 的 `AgentToolResult` 没有那个字段）。

**为什么「仍注册」而不是「不注册」**：不注册的话模型分不清「没这功能」和「缺凭据」，不会主动告诉用户去配 key。

**开关关 ⇒ 任何地方都不注册**：模型面干净，模型不会去调一个调不了的东西（先例：OpenCode `delete event.tools[name]`、Codex `create_web_search_tool` 返回 `None`）。

### D6 — 凭据判定口径

**「deepseek 已配置」当且仅当**能从下列任一处取到至少一个**非空字符串**：

1. `auth.json` 的 `deepseek` 条目：`type === "api_key"` 且**按 pi 同款语义解析后**的 `key` 是非空字符串；
2. `models.json` 的 `providers.deepseek.apiKey`（同样解析）；
3. `DEEPSEEK_API_KEY` 环境变量（非空字符串）。

**都取不到 / 条目是 `oauth` / `key` 缺失 / `!command` 或 `$VAR` 解析失败 ⇒ 判未配置。**

**优先级**（与 pi 一致）：单次请求显式 `apiKey` → **auth.json** → **models.json** → **环境变量** → 未配置。源码注释：_"A stored credential owns the provider: ambient/env is consulted only when nothing is stored."_（`pi-ai/dist/auth/resolve.js:5-8,14-39`）

**⚠️ 不得用 `readStoredCredential` 的「有没有返回条目」当判定**：它只读 auth.json 且**原样返回、不解析不校验**（`dist/core/auth-storage.js:424-432`），而 pi 内部走 `AuthStorage.read` → `resolveConfigValue` 会**执行 `!command`、插值 `$VAR`**（`:376-384`）⇒ 两种形态下**双向误判**（假阳性 + 假阴性）。本机 `models.json` 用的正是 `!command` 形态。

**实现约束**：

- 要已解析的 key 的**唯一公开路**是 `ModelRuntime.getAuth(providerId)`（根导出的公开类）。**不要用 `getProviderAuthStatus`**——快照未刷新会假阴性。
- 路径走 `getAgentDir()`，**不写死 `~/.pi/agent`**（`getAuthPath()` 未从根导出）。
- **开关关时完全不读凭据文件**（连路径都不解析）；**父会话时也完全不读**。

**泄露禁令**：key **不得**出现在工具描述、错误文案、日志、异常栈、请求 header 打印里。`WORKER_ENV_ALLOW_LIST`（`src/runtime/limits.ts:154`）已经挡住 key 类环境变量进 PTC worker，但**扩展跑在 host 进程里**，`process.env.DEEPSEEK_API_KEY` 对它可见 ⇒ 判定必须涵盖环境变量这一级，而它**绝不能被回显**。

### D7 — 配额

- **单位**：per child process。一个子代理是一个完整的 pi 进程（一个新会话）⇒ 它有一份额度。
- **不是 per-run**：配额要管「这个 child 花了多少」，不是「这次程序发了几次」。
- **默认值 30**：**按上下文定的，不是按钱定的**。概览实测 1,505–4,452 字符/次（D8）⇒ 30 次 ≈ 45k–135k 字符，正好是一个 128k 上下文装得下的检索结果量；而钱根本不是约束轴（30 × 0.005 元 = **0.15 元/child**）。**上下文才是那个先撞到墙的东西**，配额要对着它定。
- **可配**：`webDsSearch.maxCallsPerSession`，**`0` = 不限制**。与 Claude Code 的「能调高不能关」**故意不同**——本包已有一个显式总开关（D4），再叠一个不可关的配额是重复约束。
- **只在成功请求时计数**（HTTP 200）。**失败、超时与 429 不消耗配额**（这次没成功，槽位归还）。
  **本地口径比计费口径更严**：官方只对「HTTP 200 **且产生结果**」的请求计费（Search 的 `results` 必须非空、Fetch 必须返回正文），而本地把「200 但空结果」也算一次成功并扣配额 ⇒ **配额用满时实际花费 ≤ 上限**，不是恰好等于上限。
- **官方价格换算**（2026-10-20 复核官方指南页）：Search / Fetch 各 **5 元 / 千次成功请求** = **0.005 元/次**。默认 30 次 ⇒ **≤ 0.15 元/child**；父会话派 N 个 child ⇒ **≤ 0.15N 元**。
- **从上一次搜索结果里直接取的 `open` / `find` 不计数**——它们不发请求。计数的只有真的发出去的请求。
- **计数在宿主侧**（child 进程内的那一份计数器）。
- **超限不报错**，回一句：

  > 「本会话的搜索配额已用完（30 次）。请基于已经收集到的信息继续作答，并在答案里说明这一限制。」

  先例：Claude Code 配额耗尽时 _"return a notice telling it to continue with the information it already gathered and say so in its answer"_——降级不是报错，是把提示回灌给模型让它改变策略。

**⚠️ 父会话的总花费没有上界**：配额是 per child process ⇒ 父会话派出 N 个 child，最坏情况是 N × `maxCallsPerSession` 次成功请求（默认 ⇒ **≤ 0.15N 元**）。本 spec **如实写明这个乘数关系**，不去假装它是常数。

**而这个上界够不着**：0.15N 元对任何一次会话都不是一笔账。**要兜住的是上下文而不是钱**——而上下文那一侧已经由「概览 + 30 次」双管齐下压住了（D8 + 默认值）。真要兜住父会话的总额度就得引入跨进程的额度下发（父侧记额度 + 传递 + 并发派发时的分配规则），**为一个差一个数量级的上界不值得** ⇒ 见 Out of Scope。

**与 429 必须能分辨**（两者文案**不得**复用同一句）：

|          | 配额耗尽                 | 429 限速                                                                                  |
| -------- | ------------------------ | ----------------------------------------------------------------------------------------- |
| 谁说的   | **本地**                 | **服务端**（账号级 QPS：Search 100/次每秒、Fetch 25/次每秒，另 Fetch 有按目标域名的 QPS） |
| 性质     | 本地策略，可以调大       | 暂时性，等一下就好                                                                        |
| 该做什么 | 用已有信息继续作答并说明 | 等一下重试                                                                                |

**不按金额计量**：DeepSeek 的 `count` 不影响单价，次数是唯一可比的单位；按金额计量要引入价格表，会随服务端调价而漂移。

### D8 — 模型读到的是概览，深度按需取

**结构化载荷里是 DeepSeek 的 10 个字段（原样，不裁剪、不做引用装配）；模型读到的那段文本是概览。**

**为什么必须是概览**：pi 把工具结果交给模型时**只发 `content` 块**——`details` 与 `structuredContent` 留在宿主侧（pi-ai 的 `convertToolResultOutput` 只读 `content`）。所以**模型看不见的载荷等于不存在**。

**实测（2026-10-20，四次真实调用，`docs/prototypes/search-context-budget-measurements.md` §9）**：

| 做法                                        | 每次 count=10 搜索的模型可见字符 | 128k 上下文能装几次 |
| ------------------------------------------- | -------------------------------- | ------------------- |
| 只给 title + url + 阈值（Anthropic 式）     | 827–1,778                        | **292–628**         |
| **再加 `snippet`（DeepSeek 自己的短摘要）** | **1,505–4,452**                  | **116–345**         |
| 全量 `summary`（= 改形前的做法）            | 8,078–33,692                     | 15–64               |

⇒ **概览给 `snippet`，不给 `summary`。** 两个理由：

1. **`summary` 是整页摘录**（实测最长 4,757 字符，官方口径是「通常 600–800」——实测 10 条里 9 条超 800）。它当概览会把上下文一次吃掉。
2. **`snippet` 才是给模型的那一份**：它是 DeepSeek 自己算的 **query 相关**短摘要（105–414 字符），实测样本里**直接含答案**（单价、计费口径都在里面），而 `summary` 是页面元数据开头。

**深度怎么给**：`open` 给出那一页的完整 `summary`（中位 493–3,267、最大 4,757 字符），**从搜索的结果里取时零额外 API 成本、零配额**；`find` 给出那一页里命中 `pattern` 的**行号**，让模型能只取需要的那一段。

**⚠️ 记忆要跨过好几次搜索，url 要能宽松匹配**——这两条都是真机 e2e 抓出来的：

- **记忆只留最后一次搜索 ⇒ 模型会白花一次请求。** e2e 里子代理**搜了三次**才去 `open`，而它打开的是**第一次**搜索里找到的那一页。记忆若只留最后一次，那次 `open` 就退回成抓取——**模型为了一段 API 早就算好、早就计过费的文字付了一次请求**。⇒ 记忆保留**最近 5 次搜索**的结果（按 url 合并，新的覆盖旧的），并有字符上限，超了从最旧的开始丢。
- **模型不会逐字节照抄 url。** 它可能去掉结尾的 `/`、带上 `#1` 片段、带着 `utm_source` 查询串。⇒ 宽松匹配：**scheme + host 相同、path 去掉结尾 `/` 后相同、fragment 不计、query 相同或「记住的那条本来没有 query」**。两条只有 query 不同的 url **不算同一页**（否则模型会拿到错的内容）。

**概览有上限**（16,000 字符，`count` 最大 50 时才会触发）：超限时**整条**丢掉排位靠后的结果，并告知丢了多少。**绝不切碎一条**——切掉的是事实，而模型看不出它被切了；丢掉的模型看得见，而且能用 `open` 单独打开。

**`need_content` 仍然有用**：它让 API 连页面正文一起返回（正文进结构化载荷，**不进概览**），于是 `open` 能给出整页而不必再发一次请求。

### D9 — 错误文案是一份共享常量

10 个状态码各一句，**面向模型写**：

| 码  | 文案                                                                                             | 可重试 |
| --- | ------------------------------------------------------------------------------------------------ | ------ |
| 400 | 「搜索请求不合法（查询词超长或字段无效）：{message}」                                            | 否     |
| 401 | 「DeepSeek API key 无效或已失效。请在 pi 的凭据里更新后重试。」                                  | 否     |
| 402 | 「DeepSeek 账号余额不足，充值后才能继续搜索。」                                                  | 充值后 |
| 403 | 「该网页被安全策略拒绝抓取。换个来源，或改用搜索结果里的其它链接。」                             | 否     |
| 404 | 「这个网址抓不到可用内容（不可用、被站点拦截、内容类型不支持、或没有可提取的正文）。换个来源。」 | 否     |
| 408 | 「读取请求体超时，稍后重试。」                                                                   | 是     |
| 413 | 「请求体过大。缩短查询，或减少一次请求带的内容。」                                               | 否     |
| 429 | 「搜索接口超过 QPS 限制（Search 100 次/秒、Fetch 25 次/秒）。稍等后重试。」                      | 是     |
| 500 | 「搜索服务内部错误，稍后重试。」                                                                 | 是     |
| 504 | 「搜索服务下游超时，稍后重试。」                                                                 | 是     |

**「200 + 空 results」不是错误**，是一个**信号**：

> 「没有匹配到结果。换个说法，或去掉 site: / lang: / after: 之类的限定再试。」

**官方重试契约**（文案要能让人据此改变策略）：_"遇到 HTTP 408、429 或 5xx 错误时，请等待后重试。遇到 HTTP 402 时，请先充值再重试。对于其它 4xx 错误，如不修改请求，请勿重试。"_

**三条硬性约束**：

- **单一事实源**：那句「本会话未配置 DeepSeek 凭据」在**两处**出现，且是**同一份共享常量**——**工具的描述**（每会话注册一次，那一句说的是这一会话的真话）与**调用失败时抛出的那句**。测试断言两边 `toContain(同一常量)`。
- **`param` 恒为 `null`**（DeepSeek 的错误格式如此）⇒ 不能靠 `param` 定位是哪个字段错，只能读 `message` ⇒ 400 的文案**必须带上 `message`**。
- **不得泄露 key**：401 的文案只说「key 无效」，**绝不回显 key 本身或它的片段**。

**另有两类拒绝是本地的，发请求之前就发生**（官方口径的边界：<https://api-docs.deepseek.com/zh-cn/guides/search>）：

- **`count` 必须在 1–50**（越界则本地拒绝，句子说清范围与「一次多取不额外计费」）。
- **`query` 最多 128 个 Unicode 字符、且不能全为空白**（同上；长度按**码点**数，不是 UTF-16 单元）。

**为什么本地拦而不是丢给上游的 400**：上游也会拒，但那是**一次往返 + 一句 API 的话**（`"'count' must be between 1 and 50"`——它报的是内部字段名，不是范围）。本地拒绝的句子要能让模型**据此改正**。而且**本地拒绝不花钱、不占配额**（槽位是在参数通过之后才取的）。

## Testing Decisions

实现须满足 `docs/testing-constraints.md` 的 6 条硬约束。与本 spec 直接相关的：

- **失败路径必须有 warn 或显式错误状态** —— 缺凭据、401/402/403/404/413、配额耗尽，每条都要有可断言的显式状态，不留静默失败。
- **IO 边界成功/失败双路径都有单测** —— Search 与 Fetch 各测 200 / 4xx / 5xx / 429 / 402；Fetch 另测 403 与 404 的不同文案。
- **期望值能指向独立来源** —— 错误文案与 HTTP 码的映射，引用 DeepSeek 官方文档的原文（`docs/research/deepseek-search-api-20261020.md` §4），不引用实现自身。
- **反事实判据** —— 把「父会话不注册这个工具」改成「父会话也注册」，测试必须红；把「配额耗尽返回降级提示」改成抛错，测试必须红；把「缺凭据时仍注册并标注不可用」改成不注册，测试必须红。
- **同一句话必须是一个共享常量** —— 测试断言工具描述与调用失败两处 `toContain(同一常量)`（先例：`BINDING_CONTRACT`）。

**要测的边界**：

1. **父会话里没有这个工具**（开关开着也没有），**且父会话不解析凭据**（缺凭据告警不在父会话里出现）。
2. 开关关 ⇒ 任何地方都不注册，**且不读凭据文件**。
3. 开关开 + 无凭据 ⇒ 工具**在**子代理的注册表里、描述含「未配置凭据」、`ctx.ui.notify` 恰好被调用一次、调用抛出那句可读错误。
4. 凭据判定：`api_key` / `oauth` / `key` 缺失 / `!command` / `$VAR` / 环境变量 六种形态各一例——`!command` 与 `$VAR` 两例是**回归护栏**（用 `readStoredCredential` 的实现会在这两例上红）。
5. 配额：成功请求计数、失败不计数、429 不计数、Search 与 Fetch 共用计数器、**child 进程独立计数**、配额耗尽返回降级提示（不抛错）、配额文案 ≠ 429 文案。
6. 结果形状：十个字段原样透传（含 `site_name` / `date` 为 `null` 的情形）。
7. **概览**：文本里**有** `snippet`、**没有** `summary`；阈值（authority / rerank）在文本里。
   **fixture 里的 `snippet` 与 `summary` 刻意不互为子串**——否则这条断言分不出两者。
8. **`open` 从上一次搜索的结果里取**：给出的是那条的**完整 `summary`**，**且客户端一次没被问、配额一格没占**。
9. **`open` 在没搜过的 url 上**：会**抓**（客户端被问一次、配额占一格），文本里说清是现抓的。
   9b. **`open` 能找到**早前**那次搜索里的那一页**（e2e 抓到的缺陷：记忆只留最后一次时，模型会白花一次请求），**且 url 写法略有差别也认**（结尾 `/`、`#1` 片段、跟踪 query）。
10. **`find`**：给出命中行的**行号**；没命中时说清没命中并点名要找的词。
11. **概览有界**：超过 16,000 字符时**整条**丢掉排位靠后的结果，并告知丢了多少（**不切碎任何一条**）。
12. **本地参数校验**：`count` 越界（0 / 51 / -1 / 3.5）与超长 `query`（129 字符）各自被**本地拒绝**，句子说清范围；**拒绝时客户端一次没被问、配额一格没占**；`query` 的长度按**码点**数（64 个 emoji = 64 个字符，必须**被接受**——按 UTF-16 单元数会误拒）。
13. **跨版本**：`pnpm run compat:pi` 要在 0.86.0（declared floor）上仍绿——0.86.0 上 `exposure` 不存在（`docs/agents/pi-compat-matrix.md:63`）⇒ 字段被忽略、工具照样 model-facing；**而那正是我们要的**（它在子代理里），旧形状里那个「联网计费工具落到模型直接面」的风险**不存在了**，因为父会话根本不注册它。

### 端到端实测（2026-10-20，真实 pi + 真实模型 + 真实 API）

**这条缺口已闭合。** 复现命令：`pnpm run build && node scripts/verify-search-e2e.ts`（**不在默认门禁里**——它要花钱、要网络、要凭据；缺任何一样就大声失败退出，不静默通过）。

**它怎么搭的**：隔离的 agent dir（只留 deepseek 凭据 + 开关打开的 `ptc.json`）＋ PATH 上的 `pi` 包装器（真的 pi ＋ `--extension <本仓 dist/index.js>`，并把子进程的 stdout 抄一份留证）＋ **真的 `dispatch()`**（它负责给子进程打 `PI_PTC_DEPTH=1`）。

**它验了六件事**：

| 断言                                    | 证据在哪                                            |
| --------------------------------------- | --------------------------------------------------- |
| 子代理的模型调了这个工具                | 子进程 JSONL 里的 `web_ds_search` 工具执行事件      |
| 真的 API 答了                           | 工具结果的结构化载荷里有真实 URL                    |
| **API 的 `summary` 到了模型手里**       | 同一个工具结果里，模型可见的文本包含 `summary` 原文 |
| 答案回到了父会话                        | 父拿到的文本里那个 URL **就是** API 返回过的 URL    |
| **它真的「再问」了**（概览 → 打开一页） | 子代理的调用参数里有 `open`，且是它搜到的那个 url   |
| **那一次「再问」没有花钱**              | 工具结果里写着「来自上一次搜索的结果」              |

**最后一行是唯一没法伪造的一行**：父会话自己没有搜索工具，一个模型编出来的 URL 不可能出现在 API 的返回里。

**它抓出了两个真缺陷**：

1. **第一次跑**：工具给模型的文本只有 `title | url` 一行索引（数据在 `details` / `structuredContent` 里，而**pi 只把 `content` 交给模型**）⇒ 子代理明说「正文没有出现在我的上下文里」「未能从官方原文核实」。修好之后**同一条链路的子代理直接引了官方页面的原文**。⇒ D8 那条「模型读到的那段文本必须带实质」是这次实测的产物，不是先验设计。
2. **改形之后的第一次跑**：子代理**搜了三次**才去 `open`，而它打开的是**第一次**搜索里找到的那一页。**记忆只留最后一次搜索** ⇒ 那次 `open` 退回成抓取，**模型为了一段 API 早就算好、早就计过费的文字白付了一次请求**。⇒ 记忆改成跨最近 5 次搜索，并按 url 宽松匹配（结尾 `/`、`#1` 片段、跟踪 query 都认）。**两条都补了单测。**

**第二个 e2e（`scripts/verify-parent-dispatch-e2e.ts`）量的是「父会话会不会为一次搜索去派子代理」**：给父会话一个**只有 PTC 面、没有 bash** 的表面（复现 TUI 父会话的形状），问它一个必须联网的问题，看它写不写 `pi.dispatch`。量到的三件事：

1. **它会派**（先试 `tools.bash`，发现没有，转去派子代理）——但**第一次 dispatch 被拒**：父会话**自己编了一个 agent 名**（`"general"`），而「没有定义的 agent 名一律拒绝」。**根因是 PTC 工具描述里的那行示例** `await tools["pi.dispatch"]({ agent: "reviewer", task: "..." })` —— 模型照抄了那个形状。⇒ 示例改成不写名字，并写明「名字可选；不写就是 generalist；写了而没有定义会被拒」。
2. **孩子会不会用搜索模块，取决于父会话怎么写任务。** 父会话知道「孩子能 `web_ds_search`」之后，任务写的是「用 `web_ds_search` 搜」⇒ **孩子用了搜索模块**；不知道的时候，任务写的是「用 curl/bash」⇒ **孩子就 curl 了**。⇒ 工具描述里必须有那句话（`PTC_CHILD_SEARCH_NOTE`，**按会话条件化**：开关关着时不说）。
3. **抓取正文没有 8192 字符截断**（实测 6,405 / 10,282 / 9,787 字符，都完整收尾）。子代理报的「在 8192 字符处被截断」是把**工具描述里 url 的长度上限**读成了正文上限——⇒ 描述改成「这个上限是 **url** 的，不是页面的」，并且 `open` 给的是 API 的**摘要**时要说清「这是摘要、不是整页」。

改完之后同一条链路：父 → 派子代理 → 子调 `web_ds_search` → 中英文两版逐字原文回到父。

**第三个 e2e（同一个脚本，`PTC_E2E_SURFACE=codemode_ptc`）量的是「不是我们造的 PTC 模式」**（pi 自己的 codemode 激活 ⇒ 本包降为 `codemode` reach，模型直接看到的是 pi 的 `codemode` ＋ 我们的 `ptc_subagent`）。它量到的三件事里，**第 3 件是一个真缺陷，而且是本规格里「能力给到子代理」这条主张的第一次被真机证伪**：

1. **pi 自带的 codemode 确实被主动调用了**——父会话的第一反应就是写一段 codemode 脚本去派子代理，连调三次。
2. **但那三次全部失败**（`TypeError: tools.pi.dispatch does not exist`），父会话随后改用 `ptc_subagent` 才派成功。
3. **孩子根本没有搜索工具。** 父会话派单时自己加了 `readOnly: "strict"`，而 strict 名单是 `read,grep,find,ls,ptc_child_report` ⇒ pi 把孩子的 `--tools` 当**白名单**读 ⇒ `web_ds_search` 被**整个滤掉**（子进程的 `toolsAdded` 里只有那 5 个）。孩子自报「this session has no web search, web fetch, or bash tool」并放弃，父会话如实回报「我没拿到那页内容」。
   ⇒ **「孩子在 `subagents` 面上绕过搜索模块去 curl」这个说法是错的**：孩子既没有 curl 也没有搜索工具——它**没有工具**。能力不是被绕过的，是**不存在**的，而且是不存在得**静悄悄**的。
   ⇒ 修法见 [ADR-0041](../adr/0041-read-only-is-a-call-site-tier.md) §"The strict set is derived, not a constant" 的修订：strict 档在搜索模块开着时**保留** `web_ds_search`（它只读网页，不写，符合 strict 的承诺）。
4. **reach note 在上下文里也没能阻止那个 TypeError。** 它一直挂在 `ptc_run_code` 的描述里（pi 的 codemode 描述会把脚本可调的工具连同描述一起列出，所以父会话**读到了**它），父会话仍然把 `await tools["pi.dispatch"]({ task })` 抄进了脚本。原因不是它没读，而是**它上面那个例子没有作用域标记**：抄例子的模型不会去读例子下面那段话。⇒ **例子标明「inside the program」**；**reach note 先说一跳的路**（`ptc_subagent`），并让读者**看自己的工具表**。

**修完之后同一条链路（`PTC_E2E_SURFACE=codemode_ptc PTC_E2E_TASK_VARIANT=readonly`，`readonly` 这个变体就是专门为了让 strict 路径被量到的）**：父会话派单带 `readOnly: "strict"` ⇒ 孩子的工具表是 `read, grep, find, ls, ptc_child_report, web_ds_search`——**搜索工具在，`bash` 不在**（strict 的承诺没破）⇒ 孩子调了 **17 次** `web_ds_search`，自己找到并抓取了那页 ⇒ VERDICT: DISPATCHED。

## Out of Scope

- **顶层 model-facing 搜索工具（父会话里）** —— D1 明确否掉。
- **检索源可插拔** —— 抽象层、扩展点、第二家 provider（Tavily / Exa / Brave）全部不做，检索源固定为 DeepSeek Search / Fetch，不预留抽象层。理由：需求范围膨胀（2026-10-20 收缩，map #226 的基线 6）。
- **引用 / 引文格式规范** —— 不做。`url` 就在结果里，引用由模型自己装配。
- **按金额计量配额** —— D7 定为按次数。
- **父侧下发额度（把父会话的总花费兜住）** —— D7 如实写明乘数关系；**按官方价格换算后判定不值得**：要兜住的上界（默认 0.5N 元）离真实暴露差一个数量级（上下文先于配额用完，实际 0.05–0.15 元/child），而机制代价是跨进程状态与「并发派发时额度分给谁」这个没有干净答案的问题。
- **代码实现** —— 本 spec 是规格，不是实现。
