## 0. 先做一个区分，否则会得到假结论

这个实验里有两个问题，合并统计会互相污染：

| 问题                                  | 需要什么                      | 能进 CI 吗 |
| ------------------------------------- | ----------------------------- | ---------- |
| **合规**：子代理按 A/B 契约交付了吗？ | 无模型。fixture provider 即可 | 能         |
| **有用**：父级因此做得更好了吗？      | 真模型，两端都要              | 不能       |

ADR-0032 已经押过一次注：_"if models follow the prompt contract poorly, the feature is dead and CI will not have said so."_ 合规问题今天仍然只能靠真模型观察，但**它至少可以脱离父级单独测**。把两个问题分开，是这份设计的地基。

## 1. 三臂，不是两臂

建图时定的是 A/B 两臂。设计时发现**必须加第三个定标臂**，否则「差异不显著 → 两个都砍」这条规则没有可执行的触发条件——「A 和 B 差不多」不构成「两个都没用」的证据。

| 臂    | `summary`                                | 用途                               |
| ----- | ---------------------------------------- | ---------------------------------- |
| **A** | `string`，契约改为 so-what               | 候选                               |
| **B** | 结构化小对象                             | 候选                               |
| **C** | 任意形状，但内容换成**另一个任务的报告** | 定标：报告与本任务的对应关系被移除 |

判读规则（**必须在跑之前写死**）：

- `A ≈ B ≈ C` → 报告没有产生可测的价值 → **两个都砍**，回到单版（Q19 的触发器）
- `A ≈ B > C` → 报告有价值，**形状不是变量** → 选实现更省的那个
- `A > B > C` 或 `B > A > C` → 形状是变量 → 赢家胜出

C 臂是这份设计里唯一的新增，也是最有价值的一格：它把「两个都砍」从一句口号变成一次可观察的比较。

## 2. 噪声怎么造（答 Q1）

**做法**：C 臂取同批次里**另一个任务**的报告，保持 `findings` 条数相同、字符量在同一量级（±20%）。

**理由**：它同时控制三个变量——长度、格式、可信度——只移除「与本任务的对应关系」。这正是约束 5 要求的反事实：改变实现中唯一真正起作用的那一维。

被否掉的方案：

| 方案                                   | 为什么不用                                        |
| -------------------------------------- | ------------------------------------------------- |
| 直接删掉报告块                         | 同时改变「长度」和「有没有」两个变量，归因不了    |
| 等长无关文本（Lorem ipsum 类）         | 父级容易识别为垃圾并整体忽略，**低估**报告价值    |
| 把 `summary` 换成空串、保留 `findings` | 只测了 summary，没测报告整体；和 A/B 的问题不匹配 |
| 让另一个子代理现编一段假报告           | 引入第二个模型，方差翻倍，成本不可控              |

**已知偏差，要写进预注册**：C 臂的报告是「形似而内容错误」的，它可能**主动误导**父级，使 C 低于「完全没有报告」的真实基线。所以 `A > C` 说明「报告内容有用」，但**不能**直接读成「报告相对无报告的价值」。要测后者需要第四个臂，本设计明确不做，理由见 §7。

## 3. 评分卡（答 Q2）

五项，全部机械可查。**只有 R1 是判据**，其余是辅助量。

| 项            | 判据                                                         | 怎么查                                 | 角色                                        |
| ------------- | ------------------------------------------------------------ | -------------------------------------- | ------------------------------------------- |
| **R1 正确性** | 父级的最终产物是否通过任务自带的确定性检查                   | 测试通过 / 字面量相等 / 文件 diff 匹配 | **唯一判据**                                |
| **R2 引用率** | 父级最终文本里是否出现报告中的专有名词（函数名、路径、行号） | 字面量 `includes`                      | 辅助：证明「读了」                          |
| **R3 重读率** | 父级是否调用 `ptc_task_output` 或回读子代理输出              | 事件计数                               | 辅助：没读懂才会重读                        |
| **R4 合规率** | `report_channel` 与字段完整性                                | 现有解析器                             | **准入门槛**：两臂合规率差 >10pp 时实验作废 |
| **R5 token**  | 父级输入 token                                               | 现有 accumulator                       | 代理指标，不作结论                          |

每项都要有反事实：把实现改成显然错误但符合该断言的版本，测试必须红（约束 5）。例如 R2 改成「父级文本里出现 `the` 就通过」时必须红。

R4 为什么是门槛而不是判据：两个版本完全可能合规率一样而有用性不同。合规率高但没用，说明报告写得好但没价值——那正是需要看见的结果，不能被门槛挡掉。

## 4. 抽样（答 Q3）

五轴全交叉 = 3 任务类型 × 2 surface × 2 通道 × 3 agent 类型 × 2 depth = **72 格**。不可行。用分阶段。

### Stage 1 — 筛选

- 轴：**任务类型 × surface** = 6 格
- 其余三轴固定默认：通道 = `tool`，agent = generalist，depth = 0
- 每格每臂 **n = 10**
- **Stage 1 不允许产生赢家。** 它只能产生两种结论：
  - 所有格 `A ≈ B ≈ C` → 停，两个都砍
  - 某格出现差异 → 该格进入 Stage 2，其余格停

### Stage 2 — 确认

- 只跑 Stage 1 出现差异的格，每格每臂 **n = 50**
- 再单独加测被固定的三轴：通道（`tool` vs `prompt-json`）、agent 类型、depth

### 功效与判据（必须预注册）

**检验选择（2026-10-18 二次修正）**：三臂在**同一个 block（同一个任务实例）**里各跑一次，所以是配对设计。配对把任务难度这个最大的方差源消掉了：一个难任务上三臂都失败、一个易任务上三臂都成功，这些 concordant 对不进统计量。

**用 mid-P McNemar + Holm，不用 exact McNemar，也不用三次独立检验。**

- exact McNemar 过度保守（Fagerland, Lydersen & Laake 2013, _BMC Med Res Methodol_ 13:91）；mid-P 几乎和渐近版一样有功效，且未发现超过名义显著性水平。
- 三次两两比较（A-C / B-C / A-B）各自取 α=0.05 会让族错误率升到 `1-(0.95)^3 = 14.3%`。用 **Holm 逐步下降**控制到 5%；Holm 对任意依赖结构有效。

**最小不一致对 6** 有直接依据：exact 检验在 `b+c < 6` 时 p 值恒大于 0.05。mid-P 下保留这条下限——它是最小可检验样本，不是显著性阈值。

**不用序贯检验**，有公式可判：Evan Miller 的判据是计算 `1.5p + δ`，超过 36% 时固定样本更优。我们的 `p≈0.6, δ≈0.2` 给出 `1.1 ≫ 0.36`；他的表在 p=50% 时序贯的「节省」是 −85.4%。

| block 数 | 能看见的最小差异   |
| -------- | ------------------ |
| 10       | ≈ 45pp（只够筛选） |
| 30       | ≈ 26pp             |
| 50       | ≈ 20pp             |

Stage 1 的 n=10 依然只够筛，不够判——这一点没变。

### 样本顺序

随机化，不允许按日期或任务顺序成批跑——模型行为随上下文漂移，成批跑会把漂移算进臂差。

## 6. 任务样本从哪来

**每个样本必须自带确定性真值**，否则 R1 无法机械判定，实验退回人工评审。

三类：

| 类型          | 真值形态             | 例                                            |
| ------------- | -------------------- | --------------------------------------------- |
| T1 调查问答   | 可核对的字面量       | 「哪个函数持有未加锁的写路径」→ 函数名 + 行号 |
| T2 执行改文件 | 一个测试从红转绿     | 植入一个失败测试，父级须让子代理修好          |
| T3 裁决验证   | 预先植入的缺陷被指出 | 父级须说出缺陷所在行                          |

每类至少 6 个样本，任务之间的正确性互不依赖。样本本身要作为 fixture 提交，不能临时手写——否则两次运行之间样本会漂移，臂差和样本差混在一起。

## 7. 已知的坑

1. **`tests/e2e/fixtures/fake-pi.mjs` 不能产报告。** 它只发一条 `message_end`，没有 `tool_execution_end`。它能证明 prompt 契约到达了子代理，不能证明子代理照做了。用它做 A/B 会得到一个全绿的假结论。
2. **`scripts/verify-dist-render.mjs:118-125` 钉死了注册工具集。** 新增开关不能改变工具集，否则发布门禁红——这不是本实验的问题，但实现时会撞上。
3. **`vitest.config.ts:11` 的覆盖率阈值全是 0。** 覆盖率不会红，不能当反馈信号。
4. **C 臂可能主动误导**（见 §2），所以它测的是「内容对应性」，不是「报告相对无报告的价值」。
5. **`measure-session-triple.mjs:112-118` 的第四项检查是空转**（`freshCount >= 0` 恒真）。不要拿它当可复用的验证器。
6. **n = 10 是筛选，不是测量。** 见 §4。

## 9. 补丁：TUI 与版本覆盖（2026-10-18 追加）

建图后追加了一条要求：要在真实 pi TUI 里测，并覆盖从最低兼容版本到最新的全部版本。

### 9.1 两处事实更正

- **最低兼容版本是 `0.86.0`，不是 `0.89.0`。** `package.json` 的 `peerDependencies` 是 `">=0.86.0"`；`docs/agents/pi-compat-matrix.md:69` 记录该版本上 `tsc --noEmit` 0 错误、`compat:pi` 全绿。0.89.0 从来不是声明过的边界。
- **最新发布是 `1.3.0`，不是 `1.2.0`。** `scripts/pi-compat-matrix.mjs:69` 仍钉 `["0.86.0","1.0.0","1.2.0"]`，1.3.0 尚未进入矩阵。0.86.0 → 1.3.0 之间实际发布了 **15 个版本**。

### 9.2 版本是 E1 的自变量，不能外移

第一版补丁把 E1 钉在单版本、把版本覆盖推到 E2，这是错的。版本改变的是**父级看到的表面本身**：

- 0.86.0–0.87.1 没有 codemode，没有 `isError` 通道（`docs/agents/pi-compat-matrix.md:125`）
- 0.99.0 起两者都有，`ptc_run_code` / `ptc_workflow` 的暴露方式随之改变
- 报告工具、`structuredContent` 的可达性也跟着变（ADR-0032 §"What pi 1.0.0 actually offers" 的测量只在 1.0.0 上做过）

所以「哪种 `summary` 让父级做得更好」这个问题，在一个版本上得到的答案不能外推到另一个版本。版本必须进 E1。

### 9.3 但全交叉仍然不可行 —— 用分阶段 + 能力分组

把版本 × 6 格 × 3 臂 × n=50 全乘 = **13 500 次真模型运行**，每一格都欠功效。

改成三段，版本全程覆盖，但统计效力集中在需要它的地方：

| 阶段             | 版本                    | 问题                       | 每臂 n    | 能看见的最小差异 |
| ---------------- | ----------------------- | -------------------------- | --------- | ---------------- |
| **E1a 选赢家**   | 1.0.0（默认门禁测的点） | A 和 B 谁更好              | 50        | ≈ 25pp           |
| **E1b 可移植性** | **全部 15 个**          | 赢家在这些版本上是否仍然赢 | 10 / 版本 | ≈ 44pp           |
| **E1c 升级**     | E1b 中方向翻转的版本    | 翻转是真的吗               | 50        | ≈ 25pp           |

E1b 的 n=10 **只能抓大翻转**（≈44pp），抓不到细微差异。这是明写的限制，不是可以四舍五入的细节。

**能力分组提高效力**：15 个版本不是 15 个独立未知数，按能力分成四组，组内合并样本：

| 组  | 版本                              | 合并后每臂 n | 可测差异 |
| --- | --------------------------------- | ------------ | -------- |
| G1  | 0.86.0 / 0.86.1 / 0.87.0 / 0.87.1 | 40           | ≈ 22pp   |
| G2  | 0.99.0 / 0.99.1 / 0.99.2          | 30           | ≈ 25pp   |
| G3  | 1.0.0–1.0.4                       | 50（含 E1a） | ≈ 20pp   |
| G4  | 1.1.0 / 1.2.0 / 1.3.0             | 30           | ≈ 25pp   |

**判读顺序写死**：

1. E1a 选出赢家
2. E1b 逐版本跑；任一版本上赢家方向翻转 → 该版本进 E1c
3. 分组分析：如果某个能力组内赢家不同 → 结论按组给，不给全局赢家
4. 如果所有组一致 → 全局赢家成立

第 3 条是这条补丁的实质：**允许按能力组给出不同答案**，而不是强行抹平成一个赢家。这和 ticket #211 问的 surface 分叉是同一个形状的问题。

**成本**：E1a 150 + E1b 450 + E1c（按 3 个版本估算）450 ≈ **1 050 次运行**。

这个数字**不是**跑不动的理由。单次「一个子代理 + 父级收尾」约 60–90s；dispatch spike 的三子代理编排是 366–482s，那是三个子代理的全链路。按 90s 算：

- 单机串行：1 050 × 90s ≈ **26 小时**
- 8 路并行：≈ **3.3 小时**
- 机制检查（假 provider，见 §9.8）是秒级，这部分几乎不花钱

真正的成本在于**并行度**和**凭证**，不在于总数。

### 9.4 E2 仍然独立，但它回答的不是同一个问题

|          | **E1 行为 A/B**               | **E2 兼容与渲染**       |
| -------- | ----------------------------- | ----------------------- |
| 问题     | 哪种 `summary` 让父级做得更好 | 能不能用、渲染对不对    |
| 版本     | **全部 15 个**（E1b）         | 全部 15 个              |
| 样本量   | 见 §9.3                       | 每版本 n=1–3            |
| 统计结论 | 唯一承载结论的实验            | 不承载统计结论          |
| 载体     | 真模型 + RPC/JSON 驱动        | `compat:pi` 扩展 + tmux |

两者都覆盖全版本，但测的是不同层：E1 测模型行为，E2 测功能可用性与渲染。合并会同时毁掉两边的归因。

### 9.5 E1 用 RPC 驱动，不用 TUI

**修正（2026-10-18）**：第一版把 TUI 当成 E1 的驱动方式，那是错的。E1 是行为实验，需要的是可脚本化、可并行、可重复的驱动；TUI 是给人看的最后一层。

E1 的驱动统一走 **RPC**：

```bash
pi --mode rpc --no-session
```

`docs/rpc.md` 定义它是长驻子进程、双向 JSONL。E1 需要的命令全在：`prompt`、`get_state`、`get_session_stats`、`get_entries`、`fork`、`clone`、`switch_session`、`set_model`。事件侧有 `agent_settled` 可以做完成同步。

RPC 相比 `--mode json` 的关键差别：JSON 模式一次调用就退出，不能在同一个会话里追加第二轮；RPC 可以。A/B 里「同一个父级上下文，看它在报告之后做什么」需要第二轮，所以必须 RPC。

`dispatch.ts` 固定以 `--mode json -p --no-session` 启动**子代理**——子代理永远不进入 RPC 或 TUI，它是一次性进程。E1 的 RPC 驱动的是**父级**。

### 9.6 TUI 只用于 E2 的渲染核对

TUI 覆盖不是行为实验的仪器，只在最后一层用：**真 TUI 里报告块和 PTC 行到底长什么样**。

pi 提供 `--tui-mode fullscreen | regular` 两种版面，另有终端宽度变量。

驱动用 tmux——pi 官方 `docs/tmux.md` 把 tmux 列为受支持环境，`send-keys` + `capture-pane` 是一条完整的 TUI 驱动路径：

```
tmux new-session -d -s ab "pi --tui-mode fullscreen"
tmux send-keys -t ab "..." Enter
tmux capture-pane -t ab -p > frame.txt
```

仓库里没有这套基础设施（`verify-dist-render.mjs` 是 stub theme，`preview-ptc-render.mjs` 无进程），但缺口是**脚本**，不是**能力**。

**覆盖组合**：`{fullscreen, regular}` × 宽度 `{80, 100, 120}`，每格至少一帧。100 是 `verify-dist-render.mjs` 已钉的值，必须包含；80 和 120 卡折行边界。

### 9.7 仪器分工：谁测哪一层

pi 自带 `docs/cli-integration.md` 定义了四种模式，它们不是互相替代，是四个不同的测量仪器：

| 仪器                | 命令                                      | 测什么                                                    | 用在哪                        | 单次成本     |
| ------------------- | ----------------------------------------- | --------------------------------------------------------- | ----------------------------- | ------------ |
| **Canned provider** | `--provider probe --model probe-model -p` | prompt 装配、工具可见性、报告解析                         | E1 的合规门槛（R4）           | 秒级，无网络 |
| **RPC**             | `--mode rpc --no-session`                 | **多轮会话的程序化控制**：发 prompt、改模型、fork、读事件 | **E1 的全部行为测量**         | 长驻，按轮计 |
| **Print / JSON**    | `-p` / `--mode json`                      | 单次运行的最终文本与事件流                                | E1b 的轻量跑、E2 的功能可用性 | 一次调用     |
| **tmux**            | `tmux` + `--tui-mode`                     | 真实 TUI 的版面与渲染                                     | **只有 E2 的渲染核对**        | 按帧计       |

分工是一句话：**E1 用 RPC，E2 的渲染用 tmux，其余用 canned provider / JSON。**

RPC 是之前漏掉的那一个。它让「同一父级上下文、不同报告、继续一轮」可以脚本化，不需要人坐在终端前。RPC 命令里有 `fork`、`clone`、`switch_session`、`get_entries`、`get_session_stats`——这些正是配对实验需要的东西。

`--mode json` 不够用的原因很具体：它一次调用就退出，**不能在同一个会话里追加第二轮**；而"A/B 里父级在读到报告之后做什么"必须看第二轮。

**已有先例，直接抄形状**：

- `docs/research/prototype-image-delivery-ab/run.mjs` —— 三臂 A/B，canned provider，无网络，秒级
- `docs/research/dispatch-loop-e2e-spike-20261016.md` —— 真模型编排跑，记录了 wall 366–482s 与逐子代理 usage
- `scripts/pi-compat-matrix.mjs:134-163,212-245,373` —— 装多版本 pi 的机制

### 9.8 E1b 唯一真正新增的工作

装 15 个 pi 版本这件事有先例；在每个版本上**跑真模型**才是新的。`pi-compat-matrix.mjs` 跑的是仓库门禁，不跑模型；模型凭证与 provider 配置怎么带进 15 个 scratch 目录，需要设计。

但这不是"跑不动"，是"需要写一层包装"。
