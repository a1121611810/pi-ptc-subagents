# Codemode vs PTC: measured capability comparison

Date: 2026-09-30. Written after the parity audit
(`docs/research/ptc-upstream-parity-audit-20260930.md`) recorded that pi v0.99.0 ships
its own PTC. That note asked "is our work covered?". This one asks the narrower
question: **which capability wins on which axis**, measured against the two
implementations rather than against release notes.

## What was measured, and against what

Both sides are read from installed artifacts, not from documentation prose or
memory. Every row below carries a `file:line` or a named symbol.

| side          | artifact                                                                                                                                                                                             | version      |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------ |
| pi `codemode` | `/Users/lilianda/.bun/install/global/node_modules/@earendil-works/pi-coding-agent` (`dist/extensions/codemode/`)                                                                                     | `0.99.1`     |
| pi sandbox    | `/Users/lilianda/.bun/install/global/node_modules/@earendil-works/pi-codemode` (`dist/runtime/`)                                                                                                     | `0.99.1`     |
| this repo     | `src/tools/run-code.ts`, `src/tools/workflow.ts`, `src/tools/ptc-task.ts`, `src/runtime/{dispatch,dispatcher,background-runtime,limits,worker-main,worker-pool,bindings}.ts`, `src/mode/ptc-mode.ts` | working tree |

Short paths below: `pi:` = the pi-coding-agent `dist/`; `cm:` = the pi-codemode
`dist/`.

One measurement is a runtime probe rather than a read, and is marked as such:
the claim that a PTC program can reach `node:child_process`. It was verified by
compiling a function body with `new Function` in an ESM module on this repo's
Node and asking what the realm contains -- `process`, `fetch`, `setTimeout`,
`Buffer`, `globalThis.WebAssembly` present, `require` undefined, and
`await import("node:child_process")` resolving. That is the same construction
`compileProgram` uses (repo `src/runtime/worker-main.ts:458`), in the same
module kind (`src/runtime/worker-source.ts:30-47` loads an ESM file URL).

Routing is the row with a real cost on the PTC side. codemode's nested calls
inherit pi's permission pipeline; PTC's bypass it by construction, because pi's
extension API exposes no tool-dispatch surface to build on. That is a
deliberate, recorded decision (ADR-0005), not an oversight -- but it means
"call a guarded tool from a program" behaves differently on the two sides.

The two answers to "can a script start a pi subprocess" are different in kind and
the difference is worth stating precisely:

- In codemode the **script body** cannot, and that is a property of the runtime,
  not a missing feature. The VM has no module loader, so `node:child_process`
  is not merely unexposed -- it is unreachable. The only route is an injected
  tool, and the only tool that reaches a process is `bash`, whose result is a
  string. A model can therefore start a pi subprocess from a codemode script and
  get its output, but it cannot hold a handle to it, name it, list it, stop it,
  or find out what it is doing after the script ends.
- In PTC the script body _can_, directly, and that is a hole rather than a
  feature: doing it that way bypasses the depth gate, the concurrency slot and
  the task registry entirely. The supported route is the `pi.dispatch` binding,
  which is the one that carries a lifecycle.

tool's own declared `outputSchema`.

## Verdict

**codemode is a superset of PTC on isolation, on discovery, and on ergonomics.**
Three capabilities it has that PTC does not, in decreasing order of how hard they
would be to rebuilt:

1. **A language-level sandbox.** A model-written program that provably cannot
   reach the host process, a file, a socket, or a timer. This repo decided
   against shipping an OS sandbox and records the consequence as inherited risk
   (`src/runtime/limits.ts:13`, and the bindings header: "permission gates and
   sandbox overrides never run for them").
2. **Discovery at catalog scale.** `exposure: direct | model-only | codemode |
deferred | hidden`, a BM25 `searchTools`/`describeTool` pair inside the
   script, a `tool_search` tool that loads matches for the next model call, and
   auto-generated typed declarations under a token budget. PTC has a fixed
   seven-name whitelist intersected with the session's active tools, and no
   discovery surface at all.
3. **Cross-call state.** A per-branch, session-persisted `store`/`load` with
   explicit size caps. PTC's warm worker deliberately does not keep anything.

**PTC is a superset of codemode on exactly one axis, and it is the decisive
one: managed subagent lifecycle.** codemode cannot get there from where it
stands, and the reason is structural rather than budgetary.

**The single capability codemode has that PTC cannot replace:** the sandbox. A
program that is guaranteed not to touch the host. PTC's program is full Node --
the probe at the top of this note shows the realm it runs in -- so every
isolation property PTC would need is a property of the _tool bindings_, not of
the program, and any new binding is a new hole to audit.

**The single capability PTC has that codemode cannot replace:** the managed
background subagent -- `DispatchResult` for the foreground,
`{ taskId, label, status }` for the background, a 6-state `TaskRecord`,
captured output behind `OutputStorage`, owner-scoped reaping across restarts,
SIGTERM-then-SIGKILL escalation, and three always-on tools to list, read and stop
them. In codemode this is not "not implemented": the script body cannot reach a
process at all ("no Node, no file system, no network access, no timers",
`codemode/tool.js:57`), and the only tool-mediated route is `bash`, which
yields a string and no handle.

**On the "not implemented" vs "impossible" line, strictly:**

- _Impossible in the codemode runtime_, and quotable as such: the script body
  reaching a process, a file, or a network socket; a script starting a script;
  a script waiting on anything that has no pending tool call (the VM fails it
  rather than hanging).
- _Impossible in a PTC runtime_: nothing measurable. The program runs in a real
  Node worker, so anything Node can do it can do. Every PTC gap listed above is
  a gap in what the _extension exposes_, not in what the _runtime permits_ --
  with the one exception that an extension tool with no binding is genuinely
  unreachable from a program, which the repo states itself
  (`src/mode/ptc-mode.ts:75-77`).
