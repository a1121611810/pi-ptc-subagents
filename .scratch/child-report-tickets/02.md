## What to build

A PTC program can read a structured answer from a child it dispatched.

A child under the contract ends its reply with a fenced JSON block in the agreed shape. The host reads that block off the child's final message, validates it, and puts it on the dispatch result together with a statement of which channel delivered it. A program can then branch on `report.findings` instead of parsing English.

This is the first channel and the fallback for the second. It works with any model and needs nothing loaded in the child beyond the prompt, which is why it is built first rather than second.

The contract clause belongs to the tool's own description (built in the next ticket). Until that tool exists, the clause is appended to the child's system prompt, and moving it is that ticket's work rather than a second copy to maintain.

## Acceptance criteria

- [ ] The child's appended system prompt carries the contract, and the exact shape it demands is stated once
- [ ] A child's fenced JSON block is read from its final message and put on the dispatch result as `report`
- [ ] The result always states which channel delivered the report
- [ ] A program calling the dispatch binding can read a child's findings without touching the prose
- [ ] The extraction is a pure function over parsed events, so it can be driven by literal transcripts in tests
- [ ] A transcript carrying prose on both sides of the fenced block still yields the report
- [ ] A transcript carrying two fenced blocks yields the second, not the first
- [ ] A transcript whose fenced block is truncated yields no report and an explicit channel value, not a crash and not a silent prose return
