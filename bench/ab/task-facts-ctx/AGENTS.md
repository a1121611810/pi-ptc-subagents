# orders-api

> 样例项目说明（中性内容：不涉及派发/工具，只模拟真实仓库里 AGENTS.md 的体量与内容类型）

## 目录结构

- `src/` —— 业务代码，按领域分子目录（`orders/`、`pricing/`、`inventory/`）
- `tests/` —— 测试目录，单测与集成测试分开放在 `unit/` 和 `integration/`
- `docs/` —— 说明文档，面向使用者的说明放这里
- `scripts/` —— 一次性运维脚本，不进主流程

## 编码规矩

- 改代码前先把相关模块读一遍，别凭印象改。
- 公共函数的入参与返回值都要有类型标注；内部函数不强求。
- 不写「万能工具函数」：一个函数只做一件事，名字说清它做什么。
- 注释只写「为什么」，不写「做了什么」——代码本身已经说了做了什么。
- 不用调试打印提交；需要留痕就用日志，并给日志级别。
- 新增依赖前先看 `package.json` 里有没有现成的等价物。

## 风格

- 缩进两个空格，字符串用双引号，逗号结尾。
- 单行不超过 100 列。
- 提交信息第一行不超过 72 个字符，用祈使句写（`fix: ...` 而不是 `fixed ...`）。

## 测试

- 每个修 bug 的提交都要带一个能复现原 bug 的测试。
- 测试名字描述行为，不描述实现（`returns empty list when no orders` 而不是 `testGetOrders2`）。
- 跑测试前先确认依赖装齐了；CI 上跑的那套命令本地也要能跑。

## 发布

- 版本号走语义化版本；破坏性变更要在发布说明里写清楚迁移方式。
- 发布前确认 CHANGELOG 里有这一版的条目。
- 回滚方案写在发布说明里，出问题时照着执行。

## 常见坑

- 时区：服务里一律存 UTC，展示时才按用户时区转。
- 分页：偏移量分页在数据变动时会漏行，要稳定翻页得用游标。
- 重试：写下游调用必须带幂等键，否则重试会造成重复单据。
- 缓存：任何缓存都要有失效条件，别让脏数据一直挂着。

## 交接

- 接手别人的分支先跑一遍测试和 lint，别假设它是干净的。
- 提交前把改动范围说清楚：改了什么、为什么改、怎么验证的。
- 遇到看不懂的旧逻辑先问，不要顺手重构。
